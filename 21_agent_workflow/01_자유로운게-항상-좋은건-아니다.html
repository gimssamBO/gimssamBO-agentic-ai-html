자유로운 게 항상 좋은 건 아니다

한 줄 요약

지금까지의 create_agent는 LLM이 무엇을 언제 할지 스스로 결정하는 자유로운 에이전트였습니다. 탐색적 작업엔 강력하지만, "반드시 분류 후 배정" 같은 정해진 업무에는 오히려 고정 워크플로우가 맞습니다. 예측 가능하고 검증·감사가 쉽거든요.

1. 자유 에이전트의 그림자

8강부터 써 온 create_agent는 LLM이 자유롭게 도구를 골라 일했습니다. 강력하지만, 업무 자동화에는 단점이 있습니다.

자유 에이전트의 단점:
  - 예측 불가: 매 실행마다 도구 호출 순서·횟수가 달라질 수 있음
  - 검증 어려움: "반드시 분류 후 배정"이라는 규칙을 강제하기 어려움
  - 비용 변동: LLM이 루프를 몇 번 돌지 모름

탐색적 질문("이 고객에게 뭘 추천할까?")엔 이 자유로움이 강점입니다. 하지만 정형화된 반복 업무엔 오히려 독이 될 수 있죠.

2. 정해진 순서가 중요한 일

CS 티켓 처리를 생각해 봅시다.

티켓 처리 업무:
  1. 분류 (무슨 문의인가?)
  2. 우선순위 판단 (얼마나 급한가?)
  3. 담당팀 배정 (누가 처리하나?)
  → 이 순서는 반드시 지켜져야 함!

이건 순서가 정해진 업무입니다. "분류 안 하고 배정"하거나 "우선순위 건너뛰기"는 안 됩니다. 회사 규칙이니까요. 그런데 자유 에이전트는 이 순서를 보장하지 못합니다 — LLM이 가끔 순서를 건너뛰거나 바꿀 수 있죠.

3. 워크플로우 — 정해진 파이프라인

이런 업무엔 워크플로우(고정된 파이프라인) 가 맞습니다.

자유 에이전트: LLM이 "다음에 뭐 할까?" 매번 결정 (자유, 예측불가)
워크플로우:    개발자가 "분류 → 우선순위 → 배정" 순서를 고정 (정해짐, 예측가능)

워크플로우는 우리가 흐름을 미리 정합니다. "분류 다음엔 우선순위, 그 다음엔 배정"이라고 코드로 고정하죠. 그러면 항상 같은 순서로 처리되고, 검증·감사가 쉽습니다.

비유: 자유 에이전트는 재량껏 일하는 베테랑(상황 따라 융통성), 워크플로우는 체크리스트대로 일하는 신입(정해진 절차)입니다. 응급 상황엔 베테랑이 낫지만, "서류는 반드시 이 순서로 처리"하는 정형 업무엔 체크리스트가 안전하죠. 빠뜨림이 없으니까요.

4. 백엔드의 상태 머신

백엔드 개발자에게 워크플로우는 익숙한 개념입니다 — 상태 머신/처리 파이프라인입니다.

입력 → [단계 1] → [단계 2] → [단계 3] → 출력
       각 단계가 상태를 받아 일부를 채우고 다음으로 넘김

주문 처리(접수 → 결제 → 배송 → 완료), 회원가입(입력 → 검증 → 저장 → 메일) 같은 게 다 이런 파이프라인이죠. LangGraph의 StateGraph로 이걸 만듭니다.

5. 이 강에서 만들 것

CS 티켓을 분류 → 우선순위 → 배정 순서로 처리하는 워크플로우를 만듭니다.

티켓 "결제가 안 돼요"
  → 분류: 결제 (LLM)
  → 우선순위: 긴급 (규칙)
  → 배정: 결제지원팀 (규칙)

흥미로운 점: 분류만 LLM으로 하고, 우선순위·배정은 규칙(코드) 으로 합니다. "LLM이 잘하는 건 LLM에게, 규칙으로 충분한 건 코드에게"라는 분업이죠(10강 "계산은 코드"의 연장).
