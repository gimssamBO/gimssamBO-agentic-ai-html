노드 실패 처리와 상태 검증

한 줄 요약

LLM 분류 결과가 허용 카테고리 밖이면 '기타'로 보정하고, 예외가 나도 죽지 않도록 state["error"]에 기록한 뒤 파이프라인을 계속 진행합니다. 한 티켓이 실패해도 전체 배치가 멈추지 않는 견고한 워크플로우를 만듭니다.

1. 워크플로우도 실패한다

지금까지는 모든 게 잘 되는 경우(happy path)만 봤습니다. 하지만 현실에서는:

- LLM이 허용 밖 카테고리를 반환 ("음... 아마 결제 관련?")
- LLM API 호출 실패 (네트워크·타임아웃)
- 빈 티켓 내용 (입력 오류)

이런 일이 생기면 어떻게 될까요? 처리 안 하면 한 티켓의 실패가 전체 배치를 멈출 수 있습니다. 1000개 티켓을 처리하다 500번째에서 죽으면 큰일이죠.

2. 상태에 error 필드 추가

먼저 State에 오류를 기록할 필드를 추가합니다. (실습 파일: sections/21_agent_workflow/07_노드-실패-처리와-상태-검증.py)

class TicketState(BaseState):   # 기존 상태 확장
    error: str   # 오류 메시지(비어 있으면 정상)

error가 비어 있으면 정상, 뭔가 있으면 문제가 있었다는 뜻이죠. 이걸로 "어느 티켓이 어떤 문제였는지" 추적할 수 있습니다.

3. 검증 — LLM 출력을 믿지 마라

LLM 분류 결과를 검증합니다. 허용 카테고리 안에 있을 때만 채택하고, 아니면 보정하죠.

def classify_node(state: TicketState) -> dict:
    """[견고화] 분류 결과를 '검증'하고, 예외가 나도 멈추지 않는다."""
    try:
        out = llm.invoke(msg).content.strip()
        # LLM 출력은 못 믿는다 → 허용 목록 안에 있을 때만 채택
        if out in CATEGORIES:
            return {"category": out, "error": ""}
        for c in CATEGORIES:                 # 문장 속에 카테고리가 섞인 경우도 구제
            if c in out:
                return {"category": c, "error": ""}
        # 검증 실패: 허용 밖 값 → '기타'로 보정하고 사유 기록 (중단 안 함)
        return {"category": "기타", "error": f"분류값 미허용('{out[:20]}') → 기타 보정"}
    except Exception as e:
        # 한 티켓의 LLM 호출 실패해도 전체 배치가 죽으면 안 됨 → 기록 후 계속
        return {"category": "기타", "error": f"분류 예외: {e}"}

세 단계 방어:

  1. 허용 목록 검증: if out in CATEGORIES — 정확히 맞으면 채택
  2. 부분 매칭 구제: 문장에 카테고리가 섞여 있으면("아마 결제...") 추출
  3. 보정 + 기록: 그래도 안 되면 "기타"로 보정하고 사유를 error에 기록

핵심은 "LLM 출력을 그냥 믿지 않는다" 입니다(16강 환각 정신). 검증해서 이상하면 안전한 기본값("기타")으로 보정하죠.

4. 예외도 잡는다

try/except로 LLM 호출 자체가 실패해도(네트워크 등) 죽지 않게 합니다.

except Exception as e:
    # 예외가 나도 '기타'로 보정하고 사유 기록 → 파이프라인 계속
    return {"category": "기타", "error": f"분류 예외: {e}"}

예외가 나도 return으로 정상 반환합니다(예외를 다시 던지지 않음). 그러면 워크플로우가 멈추지 않고 다음 노드로 진행하죠(5·12강 폴백 정신). 한 티켓의 실패가 전체를 멈추지 않게 하는 겁니다.

5. 죽지 않음을 시연

일부러 깨진 입력(빈 내용)을 끼워 넣어 죽지 않음을 보여 줍니다.

# 의도적으로 깨진 입력을 끼워 넣어 '죽지 않음'을 시연
tickets.append({"ticket_id": "TKBAD", "content": ""})

for t in tickets:
    result = workflow.invoke({"content": t["content"], "error": ""})
    flag = result.get("error") or "정상"
    print(f"{t['ticket_id']} {result['category']} {result['priority']} {result['team']} {flag}")

예상 출력

TK001  결제     긴급   결제지원팀   정상
TK002  기타     보통   일반상담팀   정상
TKBAD  기타     보통   일반상담팀   분류값 미허용('') → 기타 보정    ← 죽지 않고 처리!

빈 티켓(TKBAD)도 죽지 않고 처리됐습니다. "기타/일반상담팀"으로 보정되고, error에 사유가 기록됐죠. 전체 배치는 끝까지 완주했습니다.

6. 노드 단위 견고성의 장점

워크플로우가 노드로 나뉘어 있어, 어느 단계에서 실패했는지 명확합니다.

error: "분류 예외: ..."     → classify_node에서 실패
error: "우선순위 예외: ..."  → priority_node에서 실패

error 메시지만 봐도 어느 노드 문제인지 즉시 압니다. 실무에서는:

  • 로깅: 실패한 티켓을 별도 로그에 기록 → 나중에 분석
  • 재시도: 일시적 실패면 그 노드만 다시 실행
  • 알림: 실패율이 높으면 담당자에게 경고
  • 수동 검토 큐: error가 있는 티켓은 "검토필요" 큐로

노드 단위라 이런 운영 장치를 깔끔히 붙일 수 있죠(02번).

7. 견고함이 진짜 서비스의 조건

happy path만 처리하는 워크플로우는 장난감입니다. 진짜 서비스는:

정상 처리(99%)도 잘하고
실패(1%)도 우아하게 다뤄야 함 (죽지 않고, 기록하고, 복구)

1000개 중 999개가 잘 돼도, 1개에서 죽어 배치 전체가 멈추면 서비스 실패죠. "검증 + 예외 처리 + 기록"으로 견고하게 만드는 게 운영 가능한 워크플로우의 조건입니다. 29강(배포)에서 이 견고성을 더 다룹니다.

핵심 정리

  • 워크플로우도 실패한다(허용 밖 분류·예외·빈 입력).
  • State에 error 필드를 둬 문제를 기록.
  • 검증: LLM 출력을 믿지 말고 허용 목록 확인, 이상하면 보정.
  • 예외 처리: try/except로 죽지 않고 기록 후 계속.
  • 노드 단위라 어느 단계 실패인지 명확(로깅·재시도·검토 큐).
  • 견고함이 진짜 서비스의 조건.
