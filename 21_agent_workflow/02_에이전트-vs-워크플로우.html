에이전트 vs 워크플로우

한 줄 요약

ReAct 에이전트는 LLM이 흐름을 동적으로 결정(자유·예측 불가), StateGraph 워크플로우는 개발자가 흐름을 엣지로 고정(정해짐·예측 가능)합니다. 탐색에는 에이전트, 정형 업무에는 워크플로우가 어울립니다.

1. 두 방식 비교

구분 ReAct 에이전트 StateGraph 워크플로우
흐름 제어 LLM이 동적으로 결정 개발자가 엣지로 고정
예측성 낮음(실행마다 다름) 높음(항상 같은 경로)
적합 작업 탐색·개방형 질문 정형화된 반복 업무
디버깅 어려움 노드 단위로 쉬움
LLM 사용 거의 모든 단계 필요한 노드에서만

2. 흐름을 누가 정하나

가장 큰 차이는 "흐름(순서)을 누가 정하느냐" 입니다.

ReAct 에이전트: LLM이 정함
  질문 → LLM "검색하자" → LLM "또 검색하자" → LLM "이제 답하자"
         (매번 LLM이 다음 행동 결정 → 실행마다 달라질 수 있음)

StateGraph 워크플로우: 개발자가 정함
  입력 → [분류] → [우선순위] → [배정] → 출력
         (엣지로 순서 고정 → 항상 이 경로)

에이전트는 LLM이 매 순간 "다음에 뭐 할까?"를 정하니 자유롭지만 예측 불가입니다. 워크플로우는 우리가 엣지로 "이 다음엔 이거"라고 못 박으니 항상 같은 경로죠.

3. 예측성의 가치

"예측 가능"이 왜 중요할까요? 업무 자동화에서는 결정적입니다.

예측 불가(에이전트): 같은 티켓도 실행마다 다르게 처리될 수 있음
  → "왜 이 티켓은 배정 안 됐지?" 디버깅 어려움
  → 감사(audit): "이 처리가 규칙대로 됐나?" 확인 어려움

예측 가능(워크플로우): 같은 입력 → 항상 같은 경로·결과
  → 디버깅 쉬움 (어느 노드에서 문제인지 명확)
  → 감사 쉬움 (규칙대로 처리됨이 보장)

금융·의료·법무처럼 "규칙대로 처리됐음을 증명" 해야 하는 분야에서는 예측 가능한 워크플로우가 필수입니다. "AI가 알아서 했어요"는 통하지 않죠.

4. 디버깅 — 노드 단위

워크플로우는 노드 단위로 나뉘어 디버깅이 쉽습니다.

에이전트: 한 덩어리 → "어디서 잘못됐지?" 찾기 어려움

워크플로우: [분류] [우선순위] [배정] 각 단계가 분리
  → "분류는 맞는데 우선순위가 틀렸네" → priority_node만 고치면 됨

각 단계가 작은 함수(노드)라, 어느 단계에서 문제인지 즉시 보입니다. 단계별 로깅·예외처리·재시도도 깔끔히 붙일 수 있죠(07번).

5. LLM은 필요한 곳에만

워크플로우의 또 다른 장점: LLM을 필요한 노드에서만 씁니다.

에이전트: 거의 모든 판단에 LLM (비용 ↑)

워크플로우:
  [분류]   → LLM (자연어 이해 필요)
  [우선순위] → 규칙 (키워드 매칭이면 충분, LLM 불필요)
  [배정]   → 규칙 (카테고리→팀 매핑, LLM 불필요)

"분류"는 자연어 이해가 필요하니 LLM을 쓰지만, "우선순위"나 "배정"은 간단한 규칙이면 충분합니다. LLM 없이 코드로 하면 빠르고 공짜이고 정확하죠. "LLM이 잘하는 것만 LLM에게"라는 분업입니다(10·11강).

6. 무엇을 언제 쓰나

작업이 정형화돼 있고 순서가 정해졌나?

  • 예 → StateGraph 워크플로우 (예측·검증·디버깅 쉬움)

  • 아니오(탐색적·개방형) → ReAct 에이전트 (자유·유연)

  • "티켓 분류 → 배정" 같은 정형 업무 → 워크플로우

  • "이 고객 문제를 어떻게 해결할까?" 탐색 → 에이전트

그리고 실무에서는 섞기도 합니다 — 워크플로우의 한 노드 안에서 에이전트를 부르는 식이죠. 둘은 대립이 아니라 상황에 맞는 도구입니다.

핵심 정리

  • 에이전트: LLM이 흐름 결정(자유·예측 불가·탐색에 강함).
  • 워크플로우: 개발자가 엣지로 흐름 고정(예측·검증·디버깅 쉬움).
  • 예측 가능성은 디버깅·감사에 결정적(정형 업무 필수).
  • 워크플로우는 LLM을 필요한 노드에만(분업, 비용↓).
  • 정형 업무는 워크플로우, 탐색은 에이전트(섞어 쓰기도).
