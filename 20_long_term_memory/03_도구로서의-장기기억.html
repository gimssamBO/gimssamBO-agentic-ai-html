도구로서의 장기 기억

한 줄 요약

장기 기억을 읽기 도구(get_profile)와 쓰기 도구(update_profile) 로 구현합니다. 에이전트가 "지금 프로필을 저장/조회해야겠다"를 스스로 판단해 도구를 호출하죠. 저장 계층(JSON→DB)을 바꿔도 도구 인터페이스만 유지하면 됩니다.

1. 두 도구

장기 기억은 두 도구로 구현합니다.

도구 역할 입력 → 출력
get_profile 프로필 조회(읽기) 고객ID → 이름/선호/비고
update_profile 프로필 갱신(쓰기) 고객ID, 필드, 값 → 저장 결과

읽기와 쓰기, 두 가지죠. 18강에서 배운 "읽기 도구는 안전, 쓰기 도구는 신중"이 여기서도 적용됩니다. update_profile은 파일에 쓰니까요.

2. 동작 흐름

[저장]

  1. 사용자: "나 선크림 알레르기 있어. 기억해줘."
  2. 에이전트: "프로필에 저장해야겠다" → update_profile(C0001, "비고", "선크림 알레르기")
  3. user_profiles.json(영속 저장소)에 "선크림 알레르기" 기록됨

[조회 — 며칠 뒤, 새 세션]

  1. 사용자: "나한테 맞는 거 추천해줘"
  2. 에이전트: get_profile(C0001) → "선크림 알레르기"를 읽어 추천에 반영

쓰기(저장)와 읽기(조회)가 영속 저장소를 통해 세션을 넘어 연결됩니다. 며칠 전 쓴 정보를 오늘 읽는 거죠.

3. 에이전트가 스스로 판단

핵심은 에이전트가 언제 저장/조회할지 스스로 판단한다는 것입니다. 시스템 프롬프트로 지침을 줍니다.

system_prompt=(
    "너는 승승장구몰 상담원이다. 한국어 존댓말로 답하라. "
    "고객이 자신의 선호/특이사항(알레르기 등)을 말하면 update_profile로 저장하라. "
    "추천이나 응대 전에는 get_profile로 고객 정보를 먼저 확인하라."
)
  • "선호/특이사항을 말하면" → update_profile로 저장
  • "추천/응대 전에는" → get_profile로 조회

이러면 에이전트가 대화를 보고 "아, 이건 저장할 정보네", "추천 전에 프로필 봐야겠네"를 스스로 판단합니다. 17강의 "필요할 때만 검색"과 같은 발상이죠 — 필요할 때만 기억을 읽고 씁니다.

4. 왜 도구 방식인가

"매 대화에 프로필을 자동으로 끼워 넣으면 안 되나?"라고 생각할 수 있습니다. 도구 방식의 장점:

  • 제어 가능: 에이전트가 "언제" 읽고 쓸지 명확 (디버깅 쉬움)
  • 효율: 필요할 때만 저장소 접근 (매번 전체 프로필 주입 안 함)
  • 선택적: 저장할 가치 있는 정보만 저장 (모든 발화를 저장 안 함)

자동 주입은 모든 대화에 프로필을 끼워 토큰을 낭비하고, 언제 저장됐는지 불투명합니다. 도구 방식은 에이전트의 판단에 따라 필요한 순간에만 작동하죠.

5. 저장 계층 분리 — 의존성 역전

가장 중요한 설계 원칙입니다. 도구 인터페이스(시그니처)는 고정하고, 내부 저장 방식만 바꿀 수 있게 합니다.

@tool
def get_profile(customer_id: str) -> str:   # ← 이 시그니처는 고정
    """프로필 조회."""
    data = _load()           # ← 내부 구현 (JSON? SQLite? 바꿔도 됨)
    ...

get_profile/update_profile의 겉모습(시그니처) 은 그대로 두고, 내부의 _load/_save만 JSON→SQLite→PostgreSQL로 교체할 수 있습니다(06번). 그러면 에이전트 코드는 전혀 안 바꿔도 저장소가 업그레이드되죠.

이걸 의존성 역전이라고 합니다. 에이전트는 "프로필을 읽고 쓴다"는 추상적 인터페이스에만 의존하고, "JSON 파일이냐 DB냐"는 세부 구현을 모릅니다. 그래서 구현을 자유롭게 바꿀 수 있죠. 백엔드의 Repository 패턴과 같은 발상입니다.

6. 원본 보호

쓰기 도구는 위험하므로(18강), 실습에서는 원본을 보호합니다.

SRC = DATA / "user_profiles.json"        # 원본 (읽기 전용)
STORE = DATA / "user_profiles_rw.json"   # 복사본 (실제 읽고/쓰기)

원본(SRC)은 건드리지 않고, 복사본(STORE)에만 읽고 씁니다. 실습 중 잘못 써도 원본이 안전하죠(18강 "복사본에만 쓰기"). 운영에서도 "마이그레이션으로 초기 데이터를 만들고, 운영 DB에서 변경"하는 식으로 분리합니다.

핵심 정리

  • 장기 기억 = get_profile(읽기) + update_profile(쓰기) 두 도구.
  • 에이전트가 언제 저장/조회할지 스스로 판단(시스템 프롬프트 지침).
  • 도구 방식: 제어 가능·효율·선택적(자동 주입보다 명확).
  • 의존성 역전: 도구 시그니처 고정, 내부 저장 방식만 교체(JSON→DB).
  • 쓰기는 위험하니 원본 보호(복사본에 쓰기).
  • 다음 절에서 프로필 저장 도구를 만듭니다.
