SQLite로 장기 기억 옮기기

한 줄 요약

JSON 파일은 매번 전체를 읽고 씁니다. 데이터가 커지거나 동시 접근이 생기면 위험하죠. SQLite(설치 없이 파일 하나로 쓰는 내장 DB)로 옮기면, 레코드 단위 조회·갱신이 가능해 안전합니다. 핵심은 도구 인터페이스는 그대로 두고 내부만 교체하는 것입니다.

1. JSON의 한계

04번의 JSON 방식은 간단하지만 문제가 있습니다.

JSON: 한 명의 비고를 바꾸려 해도
  → 파일 전체를 읽고(_load) → 수정 → 파일 전체를 씀(_save)

데이터가 작으면 괜찮지만:

  • 데이터가 크면: 고객 10만 명이면 매번 10만 명 전체를 읽고 씀(느림)
  • 동시 접근: 두 요청이 동시에 쓰면 한쪽 변경이 덮어써짐(데이터 손실)
  • 부분 조회 불가: "VIP 고객만" 같은 조건 검색이 어려움

실무 규모에서는 레코드(행) 단위로 다루는 DB가 필요합니다.

2. SQLite — 파일 하나짜리 DB

SQLite는 설치 없이 파일 하나로 쓰는 내장 데이터베이스입니다. 파이썬 표준 라이브러리(sqlite3)에 들어 있어 바로 쓸 수 있죠.

JSON: profiles.json (전체를 한 덩어리로)
SQLite: profiles.db (행 단위로 조회·갱신 가능, 동시성 안전)

서버를 띄울 필요도, 설치할 것도 없습니다. 파일 하나가 곧 DB죠. 소규모~중규모에 딱 좋고, 나중에 PostgreSQL 같은 큰 DB로 가는 디딤돌이 됩니다.

3. 테이블 만들기 + JSON 이관

(실습 파일: sections/20_long_term_memory/06_SQLite로-장기기억-옮기기.py) 테이블을 만들고, 기존 JSON 데이터를 한 번 옮깁니다.

import sqlite3, json
from common import DATA

DB = DATA / "profiles.db"

def init_db():
    """profiles 테이블을 만들고, 비어 있으면 JSON 원본을 한 번 이관한다."""
    with sqlite3.connect(DB) as conn:
        # customer_id를 기본키(PK)로 → 고객당 한 행만 존재
        conn.execute(
            "CREATE TABLE IF NOT EXISTS profiles ("
            " customer_id TEXT PRIMARY KEY, name TEXT, membership TEXT,"
            " 선호카테고리 TEXT, 관심사 TEXT, 비고 TEXT)")
        # 비어 있으면 JSON → SQLite 이관 (최초 1회)
        if conn.execute("SELECT COUNT(*) FROM profiles").fetchone()[0] == 0:
            data = json.load(open(DATA / "user_profiles.json", encoding="utf-8"))
            for cid, p in data.items():
                conn.execute("INSERT INTO profiles VALUES (?,?,?,?,?,?)",
                    (cid, p.get("name",""), p.get("membership",""),
                     json.dumps(p.get("선호카테고리",[]), ensure_ascii=False),
                     p.get("관심사",""), p.get("비고","")))
  • PRIMARY KEY: customer_id를 기본키로 둬 고객당 한 행만(중복 방지)
  • 선호카테고리는 JSON 문자열로: 리스트라 컬럼 하나에 담기 위해 json.dumps로 직렬화

4. 도구를 SQLite로 재구현

핵심: 도구 시그니처는 04번과 똑같이 두고, 내부만 SQLite로 바꿉니다(03번 의존성 역전).

@tool
def get_profile(customer_id: str) -> str:   # ← 시그니처는 04번과 동일!
    """고객ID로 SQLite에 저장된 프로필을 조회한다."""
    with sqlite3.connect(DB) as conn:
        conn.row_factory = sqlite3.Row       # row["컬럼명"]으로 접근
        row = conn.execute("SELECT * FROM profiles WHERE customer_id=?",
                           (customer_id,)).fetchone()
    if not row:
        return f"{customer_id} 프로필이 없습니다."
    p = dict(row)
    p["선호카테고리"] = json.loads(p["선호카테고리"] or "[]")   # 다시 리스트로
    return json.dumps(p, ensure_ascii=False)

SELECT ... WHERE customer_id=?로 그 고객 한 행만 조회합니다. JSON처럼 전체를 읽지 않죠. 데이터가 많아도 빠릅니다(특히 PK 인덱스 덕분).

도구의 겉모습(get_profile(customer_id) -> str)은 04번과 똑같습니다. 그래서 에이전트 코드는 전혀 안 바꿔도 됩니다. 저장소만 JSON→SQLite로 업그레이드한 거죠.

5. SQL 인젝션 방어

쓰기 도구에서 중요한 보안 포인트가 있습니다.

@tool
def update_profile(customer_id: str, field: str, value: str) -> str:
    # [경고] 컬럼명(field)을 외부 입력 그대로 SQL에 끼우면 인젝션 위험!
    allowed = {"name", "membership", "선호카테고리", "관심사", "비고"}
    if field not in allowed:                  # 허용 컬럼만 화이트리스트
        return f"'{field}'은(는) 갱신할 수 없는 필드입니다."
    with sqlite3.connect(DB) as conn:
        conn.execute(f"UPDATE profiles SET {field}=? WHERE customer_id=?",
                     (value, customer_id))    # value는 ? 파라미터로 (안전)
    return f"저장했습니다."

두 가지 방어:
- 컬럼명(field)은 화이트리스트: field를 SQL에 직접 끼우면 위험하니, 허용된 컬럼만 통과
- 값(value)은 ? 파라미터: 값을 SQL에 직접 안 넣고 ?로 바인딩(SQL 인젝션 방지)

value를 f"... SET {field}='{value}'"처럼 직접 끼우면, 악의적 입력으로 DB를 조작할 수 있습니다(10강 보안 정신). ? 파라미터를 쓰면 SQLite가 안전하게 처리하죠. 쓰기 도구는 이렇게 신중해야 합니다(18강).

6. 같은 실험, 같은 결과

SQLite로 바꿔도 05번의 실험은 똑같이 작동합니다.

1단계: update_profile → SQLite DB에 저장
2단계: 새 에이전트 → get_profile → DB에서 읽어 답변 (기억!)

저장소가 JSON이든 SQLite든, "새 에이전트도 기억한다"는 장기 기억의 본질은 같습니다. 단지 SQLite가 동시성·조회·확장에 더 강할 뿐이죠. 그리고 도구 시그니처를 고정한 덕분에, 이 교체에 에이전트 코드 변경이 전혀 없었습니다.

7. 다음 단계 — PostgreSQL 등

SQLite도 한계가 있습니다. 여러 서버가 동시에 접근하거나, 초대규모면 PostgreSQL·MySQL 같은 서버형 DB가 필요하죠.

소규모·단일 서버 → SQLite (파일 하나, 간단)
대규모·다중 서버 → PostgreSQL/MySQL (서버형, 강력)

하지만 원리와 도구 인터페이스는 그대로입니다. get_profile/update_profile의 내부를 PostgreSQL 쿼리로 바꾸기만 하면 되죠. 의존성 역전 덕분에, 저장소는 규모에 맞게 자유롭게 갈아탑니다.

핵심 정리

  • JSON은 매번 전체를 읽고 써 대규모·동시 접근에 약함.
  • SQLite(파일 하나 내장 DB)로 행 단위 조회·갱신 → 안전·빠름.
  • 도구 시그니처 고정, 내부만 교체(의존성 역전) → 에이전트 코드 불변.
  • 보안: 컬럼명은 화이트리스트, 값은 ? 파라미터(SQL 인젝션 방지).
  • 더 큰 규모는 PostgreSQL 등 — 원리·인터페이스는 동일.
