대량 검색과 인덱스 저장

한 줄 요약

14강에서 FAQ 10개는 numpy로 충분했지만, 사내 문서가 늘면 청크가 수천 개가 됩니다. 그러면 ① 매번 전체 비교가 느리고, ② 매 요청마다 다시 임베딩하면 비용이 폭발합니다. 벡터 데이터베이스가 이 둘을 해결합니다.

1. numpy 검색의 한계

14강에서는 FAQ 10개를 numpy 루프로 검색했습니다. 10개니까 빨랐죠. 그런데 승승장구몰의 모든 문서를 모으면?

환불정책 + 핸드북 + 멤버십정책 + 제품매뉴얼 여러 개 ...
→ 청크가 금세 수천 ~ 수만 개!

여기서 두 가지 문제가 터집니다.

① 속도 문제

매 질문마다 수천 개 벡터와 일일이 코사인 유사도를 계산하면 느립니다. 질문 하나에 몇 초씩 걸리면 서비스로 못 씁니다.

② 재인덱싱 문제

더 심각한 문제입니다. 서버가 요청을 받을 때마다 PDF를 다시 로드·임베딩하면? 임베딩 API를 매번 호출하니 비용·지연이 폭발합니다.

# 끔찍한 코드 — 요청마다 전체 재임베딩!
def handle_request(question):
    chunks = load_and_chunk_all_pdfs()    # 매번 PDF 로드
    vectors = embed(chunks)               # 매번 임베딩 (API 비용!)
    return search(vectors, question)      # 그제서야 검색

이러면 질문 하나당 수천 개를 임베딩하니, 돈도 시간도 막대하게 듭니다.

2. 벡터DB가 해결하는 것

벡터 데이터베이스(Vector DB) 는 이 둘을 모두 해결합니다.

  • 인덱스를 미리 만들어 두고(영속화) → 재임베딩 안 함
  • 근사 최근접 이웃(ANN) 알고리즘으로 검색 → 빠름
[사전 1회] PDF → 청킹 → 임베딩 → 벡터DB 인덱스 → 디스크 저장
[매 요청]  디스크에서 로드 → 질문만 임베딩 → 빠르게 검색

핵심은 13강에서 배운 그 원리입니다 — "비싼 계산은 미리 해서 저장, 요청 시엔 조회만." 백엔드 개발자에게 익숙한 패턴이죠.

비유: 도서관과 같습니다. 사서가 책을 미리 분류해 서가에 꽂아 두면(인덱싱), 손님이 올 때마다 빠르게 찾아 줍니다. 손님이 올 때마다 책을 다시 분류하지 않죠. 벡터DB가 그 "미리 분류된 서가"입니다.

핵심 정리

  • 문서가 늘면 청크가 수천 개 → numpy 검색은 느리고 매번 재임베딩은 비쌈.
  • 벡터DB가 해결: 인덱스 미리 저장(재임베딩 X) + 고속 검색(ANN).
  • 원리: "비싼 계산은 미리, 요청 시엔 조회만"(13강 인덱싱/질의).
