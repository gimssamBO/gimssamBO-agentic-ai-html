벡터DB의 역할

한 줄 요약

벡터DB의 핵심은 인덱싱(사전 1회)과 서비스(매 요청)를 분리하는 것입니다. 인덱싱은 느리고 비싸지만 한 번만 하고, 검색은 빠르고 싸서 매 요청마다 합니다. 이 분리가 RAG를 실용적으로 만듭니다.

1. 두 시점의 분리

벡터DB는 두 가지 일을 다른 시점에 합니다.

  • ■ 사전 인덱싱 (1회/배치 — 느리고 비쌈)
    PDF들 → 청킹 → 임베딩 → 벡터DB 인덱스 → save → 디스크(인덱스 파일)
  • ■ 서비스 (매 요청 — 빠르고 쌈, 반복)
    디스크(인덱스 파일) → load → 벡터DB 인덱스 → 질문 임베딩 → Top-k 검색

13강에서 배운 "인덱싱 vs 질의"가 벡터DB에서 구체화된 모습입니다.

2. 인덱싱 — 무겁지만 한 번만

인덱싱은 문서를 검색 가능한 형태로 만드는 사전 작업입니다.

# 인덱싱: 느리고 비싸지만 한 번만
chunks = load_and_chunk(pdfs)        # 로드 + 청킹
vs = FAISS.from_documents(chunks, emb)  # 임베딩 + 인덱스 생성 (여기서 비용 발생!)
vs.save_local("faiss_index")         # 디스크에 저장

이 과정은 임베딩 API를 호출하므로 시간과 비용이 듭니다. 하지만 딱 한 번만 하면 됩니다. 문서가 바뀌지 않는 한 다시 할 필요가 없죠.

3. 서비스 — 가볍고 매번

서비스는 저장된 인덱스로 검색하는 작업입니다.

# 서비스: 빠르고 싸서 매 요청마다
vs = FAISS.load_local("faiss_index", emb, ...)  # 저장된 인덱스 로드 (재임베딩 X!)
results = vs.similarity_search("질문", k=3)       # 빠른 검색

여기서 핵심: load_local은 임베딩을 다시 하지 않습니다. 저장된 벡터를 그대로 읽죠. 그래서 빠르고 쌉니다. 질문 하나만 임베딩하고, 미리 만든 인덱스에서 빠르게 검색합니다.

4. 근사 최근접 이웃(ANN) — 빠른 검색의 비결

벡터DB가 빠른 이유는 ANN(Approximate Nearest Neighbor, 근사 최근접 이웃) 알고리즘 덕분입니다.

정확한 검색: 수만 개 벡터와 일일이 비교 → 정확하지만 느림
ANN 검색:    똑똑한 구조로 "가까운 후보만" 빠르게 추림 → 약간의 오차, 매우 빠름

14강 numpy 루프는 모든 벡터와 비교(정확하지만 느림)했습니다. ANN은 미리 만든 자료구조로 유망한 후보만 빠르게 찾습니다. 약간의 정확도를 양보하고 속도를 크게 얻는 거죠. 수만 개에서도 밀리초 단위로 검색합니다.

비유: 사전에서 단어를 찾을 때, 첫 페이지부터 다 넘기지(numpy 루프) 않고 "ㄱ 섹션"으로 바로 가서(ANN) 찾는 것과 같습니다. 약간 다른 위치를 펴도 근처라 금방 찾죠. 전체를 다 보지 않아 훨씬 빠릅니다.

5. 왜 이 분리가 중요한가

인덱싱과 서비스를 분리하지 않으면 어떻게 될까요?

# 분리 안 함 (끔찍) — 요청마다 인덱싱
def handle(question):
    vs = FAISS.from_documents(load_and_chunk(pdfs), emb)  # 매번 임베딩!
    return vs.similarity_search(question)

# 분리함 (올바름) — 인덱싱 1회, 검색 매번
vs = FAISS.load_local("faiss_index", emb, ...)  # 서버 기동 시 1회
def handle(question):
    return vs.similarity_search(question)         # 검색만

분리하면 서버 기동 시 인덱스를 한 번 로드하고, 이후 요청은 검색만 합니다. 빠르고 싸죠. 이 분리가 RAG를 실제 서비스로 쓸 수 있게 만드는 핵심입니다(04번에서 더 자세히).

핵심 정리

  • 벡터DB는 인덱싱(사전 1회) 과 서비스(매 요청) 를 분리한다.
  • 인덱싱은 무겁지만 한 번만(임베딩 비용), 서비스는 가볍고 매번(검색만).
  • load_local은 재임베딩 안 함 — 저장된 벡터를 그대로 읽음.
  • ANN 알고리즘으로 수만 개에서도 빠르게 검색.
  • 이 분리가 RAG를 실제 서비스로 만든다.
