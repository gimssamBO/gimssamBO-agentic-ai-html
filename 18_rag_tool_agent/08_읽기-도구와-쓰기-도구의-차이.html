읽기 도구와 쓰기 도구의 차이

한 줄 요약

읽기 도구(조회)는 데이터를 안 바꿔 안전합니다. 쓰기 도구(상태 변경)는 위험합니다 — 잘못 실행하면 돈이 나가고 되돌리기 어렵죠. 쓰기 도구는 (1) 원본을 건드리지 않고 복사본에만, (2) 실행 전 확인 절차를 두어 안전하게 만듭니다.

1. 읽기 vs 쓰기

지금까지 모든 도구는 읽기였습니다. 쓰기는 차원이 다릅니다.

읽기 도구: get_order_status("O")  → 조회만 (데이터 안 바뀜) → 안전
쓰기 도구: cancel_order("O")      → 상태를 '취소'로 변경 → 위험!

읽기는 몇 번 호출해도 부작용이 없습니다(멱등, 04번). 하지만 쓰기는 한 번 한 번이 진짜 영향을 줍니다. 주문을 취소하고, 환불을 실행하고, 돈을 움직이죠. 잘못 실행하면 큰 사고입니다.

비유: 읽기는 서류를 읽는 것(아무리 읽어도 서류는 그대로), 쓰기는 서류에 도장을 찍는 것(한 번 찍으면 되돌리기 어려움)입니다. 도장은 신중히 찍어야 하죠.

2. 왜 LLM에게 쓰기를 맡기면 위험한가

LLM은 가끔 실수합니다. 읽기 도구라면 실수해도 "엉뚱한 조회" 정도로 끝나지만, 쓰기 도구는 실수가 곧 사고입니다.

LLM이 잘못 판단 → cancel_order("O0001") 잘못 호출
  → 멀쩡한 주문이 취소됨! → 고객 불만 → 되돌리기 복잡

그래서 쓰기 도구는 LLM이 함부로 실행하지 못하게 안전장치를 둬야 합니다. 두 가지 장치를 봅시다.

3. 안전장치 ① — 복사본에만 쓰기

(실습 파일: sections/18_rag_tool_agent/08_읽기-도구와-쓰기-도구의-차이.py) 원본 데이터를 절대 건드리지 않고, 메모리 복사본에만 변경을 적용합니다.

_orders_원본 = pd.read_csv(DATA / "orders.csv", encoding="utf-8-sig")
orders = _orders_원본.copy()   # [핵심] 쓰기는 '복사본'에만 한다

@tool
def confirm_cancel_order(order_id: str) -> str:
    """주문 상태를 '취소'로 변경한다."""
    # 원본(_orders_원본)이 아니라 복사본(orders)만 바꾼다
    orders.loc[orders["order_id"] == order_id, "status"] = "취소"
    return f"주문 {order_id} 취소 완료(복사본에만 반영)."

복사본에만 쓰니, 실습 중 잘못 실행해도 원본 CSV는 훼손되지 않습니다. 실전에서도 "테스트 환경(복사본)에서 먼저 검증하고 운영(원본)에 반영"하는 식으로 분리하죠.

4. 안전장치 ② — 2단계 확인 절차

가장 중요한 장치입니다. 쓰기를 "요청"과 "확정" 두 단계로 나눠, 실행 전 확인을 받습니다.

_대기중_취소 = {}   # 보류 중인 취소 요청

@tool
def request_cancel_order(order_id: str) -> str:
    """[1단계] 취소를 '요청'만 한다(아직 변경 안 함). 확인이 필요하다."""
    cur = orders[orders["order_id"] == order_id].iloc[0]["status"]
    _대기중_취소[order_id] = cur
    return (f"주문 {order_id}(현재: {cur}) 취소를 요청했습니다. "
            f"정말 취소하시겠습니까? 확정하려면 confirm_cancel_order를 호출하세요.")

@tool
def confirm_cancel_order(order_id: str) -> str:
    """[2단계] 1단계 요청을 확정해 상태를 '취소'로 변경한다."""
    if order_id not in _대기중_취소:   # 1단계 요청이 없으면 막음
        return f"먼저 request_cancel_order로 요청하세요."
    orders.loc[orders["order_id"] == order_id, "status"] = "취소"
    return f"주문 {order_id} 취소 완료."

흐름:
1. 요청(request_cancel_order): "정말 취소할까요?" 묻고 보류만 함 (아직 안 바꿈)
2. 확정(confirm_cancel_order): 사용자 동의 후에만 실제 변경

1단계 요청 없이는 2단계 확정이 막힙니다. 그래서 LLM이 실수로 한 번에 취소할 수 없죠. 사람이 "네, 취소해 주세요"라고 동의해야 실행됩니다.

비유: 은행 송금과 같습니다. 금액을 입력(요청)한 뒤, "정말 송금하시겠습니까?"에 한 번 더 확인(확정)을 받죠. 한 번의 클릭으로 큰돈이 나가면 안 되니까요.

5. 시스템 프롬프트로 강제

도구 설계뿐 아니라 시스템 프롬프트로도 신중함을 지시합니다.

system_prompt=(
    "너는 승승장구몰 CS 에이전트다. 조회는 get_order_status로 한다. "
    "주문 취소는 반드시 request_cancel_order로 먼저 확인을 받고, "
    "사용자가 동의하면 confirm_cancel_order로 확정하라. 함부로 확정하지 마라."
)

"먼저 확인받고, 동의하면 확정하라, 함부로 하지 마라"라고 명시합니다. 도구의 2단계 구조 + 프롬프트의 신중 지시가 겹쳐, 쓰기 사고를 이중으로 막죠(심층 방어, 3강).

6. 실무의 쓰기 도구 원칙

실무에서 쓰기 도구를 만들 때 지킬 원칙:

  • 확인 절차: 중요한 변경은 사람 확인 후 실행(2단계)
  • 권한 분리: 아무나 못 쓰게 권한 검사
  • 감사 로그: 누가 언제 무엇을 바꿨는지 기록
  • 롤백 가능성: 되돌릴 수 있게 변경 전 상태 보관
  • 테스트 환경 분리: 운영 데이터를 직접 안 건드림

읽기 도구는 이런 게 거의 필요 없지만, 쓰기 도구는 겹겹의 안전장치가 필수입니다. "조회는 마음껏, 변경은 신중히"가 안전한 에이전트의 철칙입니다.

핵심 정리

  • 읽기(조회)는 안전, 쓰기(상태 변경)는 위험(되돌리기 어려움).
  • LLM 실수가 쓰기 도구에선 곧 사고 → 안전장치 필수.
  • 안전장치 ①: 복사본에만 쓰기(원본 보호).
  • 안전장치 ②: 2단계 확인(요청 → 동의 → 확정).
  • 시스템 프롬프트로도 신중함 지시(심층 방어).
  • 실무: 확인·권한·감사·롤백·환경 분리.
