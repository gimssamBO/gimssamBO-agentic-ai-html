문서 검색과 실시간 데이터를 한 에이전트에

한 줄 요약

실전 CS는 "문서(정책)"와 "실시간 데이터(주문·재고)"를 동시에 필요로 합니다. "환불 절차랑 내 주문 상태 알려줘" 같은 질문이죠. 정답은 RAG도 "도구의 하나"로 보고, 다른 데이터 도구들과 같은 도구 목록에 넣는 것입니다. 13~18강 RAG 파트의 종착점입니다.

1. 두 출처가 섞인 질문

고객이 이렇게 묻습니다.

"어제 받은 이어버드 환불하고 싶은데, 절차랑 제 주문 O000902 상태 좀 알려주세요."

이 한 문장에 두 가지 출처가 섞여 있습니다.

  • "환불 절차" → 사내 정책 문서(RAG)에 있음
  • "주문 O000902 상태" → 실시간 DB(orders.csv) 에 있음
문서만 검색하는 17강 에이전트 → 주문 상태를 모름
도구만 있는 9·12강 에이전트   → 정책을 모름
실전 → 둘을 함께 써야 함!

17강의 Knowledge Agent는 문서만, 12강의 멀티툴 에이전트는 데이터만 다뤘습니다. 실전 상담은 둘을 함께 써야 하죠.

2. 정답 — 모두 같은 도구 목록에

해결책은 놀랄 만큼 단순합니다. RAG도 도구의 하나로 보고, 데이터 도구들과 같은 목록에 넣는 것입니다.

tools = [
    build_policy_tool(),    # RAG 검색 도구 (정책 문서)
    get_order_status,       # DB 조회 도구 (주문)
    get_stock,              # DB 조회 도구 (재고)
]
agent = create_agent(llm, tools=tools, ...)

세 도구를 한 목록에 넣으면, 에이전트가 질문을 분석해 필요한 도구를 골라가며 답합니다. "환불 절차"엔 policy_search를, "주문 상태"엔 get_order_status를 쓰는 식이죠.

3. 핵심 통찰 — 모두 '함수'다

이게 가능한 이유는 17강에서 RAG를 도구로 만들었기 때문입니다.

에이전트 입장에서 RAG든 DB 조회든 재고 확인이든 전부 "호출하면 결과를 주는 함수" 다.

policy_search("환불 절차")     → "환불은 7일 이내..."
get_order_status("O000902")    → "배송완료"
get_stock("이어버드")          → "재고 225개"

겉보기엔 RAG(문서 검색)와 DB 조회가 완전히 다른 일 같지만, 에이전트에게는 똑같은 도구입니다. 17강에서 RAG를 도구로 포장했으니, 이제 다른 도구들과 자연스럽게 섞이죠. 이게 "모든 능력을 도구로 통일"하는 발상입니다(02번).

4. RAG 파트의 종착점

13~18강의 RAG 여정이 여기서 완성됩니다.

13강: RAG 개념 (로드·청킹)
14강: 임베딩
15강: 벡터DB
16강: RAG QA (생성)
17강: RAG를 도구로
18강: RAG 도구 + 데이터 도구 통합  ← 종착점!

이제 진짜 CS 에이전트가 됩니다 — 사내 문서 지식(RAG)과 실시간 데이터(DB)를 함께 다루는 종합 상담봇이죠. 1부(도구)와 RAG 파트가 하나로 합쳐지는 순간입니다.

특히 08번에서 "쓰기 도구"의 위험성을 다룹니다. 지금까지 도구는 모두 "조회(읽기)"였는데, "환불 실행" 같은 상태 변경(쓰기) 은 신중해야 하거든요.
