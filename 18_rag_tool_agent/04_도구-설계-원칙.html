도구 설계 원칙 (백엔드)

한 줄 요약

실전 도구는 네 가지 원칙을 지켜야 합니다: 명확한 설명 · 입력 검증과 예외 처리 · 결정적 반환 · 부작용 최소화. 특히 "조회는 읽기 전용, 상태 변경은 신중히"가 안전한 에이전트의 핵심입니다.

1. 네 가지 설계 원칙

원칙 이유
명확한 docstring/description 에이전트가 도구 선택의 근거로 삼음
입력 검증·예외 처리 없는 주문번호·상품에도 안전한 메시지 반환
결정적(deterministic) 반환 같은 입력 → 같은 출력(재현성·디버깅)
부작용 최소화 조회는 읽기 전용. 상태 변경은 별도 권한·확인

6강에서 배운 도구 설계 원칙의 실전 백엔드 버전입니다. 하나씩 봅시다.

2. 원칙 ① — 명확한 설명 (6강 복습)

도구의 docstring/description은 에이전트가 도구를 고르는 근거입니다(6·17강).

@tool
def get_order_status(order_id: str) -> str:
    """주문번호(order_id)로 주문 상태/상품/날짜를 조회한다. 예: 'O000902'"""
    # 독스트링에 '무엇을' + '입력 형식 예시'(예: 'O000902')까지 명확히 적는다.

"예: 'O000902'" 처럼 입력 형식 예시를 주면, 에이전트가 인자를 올바르게 채웁니다. 여러 도구가 함께 있을 때(18강) 각 설명이 또렷이 구별돼야 라우팅이 정확하죠.

3. 원칙 ② — 입력 검증·예외 처리

도구는 잘못된 입력에도 죽지 않고 안내해야 합니다(5·12강 복습).

@tool
def get_order_status(order_id: str) -> str:
    """주문번호로 주문 상태를 조회한다."""
    row = orders[orders["order_id"] == order_id.strip()]
    if row.empty:
        return f"주문번호 {order_id} 를 찾을 수 없습니다."   # 없어도 안전한 메시지
    ...

없는 주문번호여도 예외(KeyError)로 죽지 않고, 친절한 안내를 돌려줍니다. 에이전트가 그 안내를 받아 "주문번호를 다시 확인해 주세요"라고 폴백하죠(12강).

4. 원칙 ③ — 결정적 반환

같은 입력에는 항상 같은 출력이 나와야 합니다. 이를 결정적(deterministic) 이라고 합니다.

get_order_status("O000902")   # 항상 같은 결과 (DB가 안 바뀌면)

결정적이면 좋은 점:
- 재현성: 같은 질문에 같은 답 → 신뢰
- 디버깅: 문제가 생기면 재현해 추적 가능
- 테스트: 예상 결과를 미리 알 수 있음

그래서 조회 도구는 보통 temperature 같은 무작위성이 없습니다. DB를 그대로 읽어 돌려주니 항상 같죠.

5. 원칙 ④ — 부작용 최소화 (가장 중요)

가장 중요한 원칙입니다. 조회(읽기)는 안전하지만, 상태 변경(쓰기)은 위험합니다.

# 읽기 도구 — 안전 (데이터를 안 바꿈)
get_order_status("O000902")   # 조회만, 몇 번 호출해도 부작용 없음

# 쓰기 도구 — 위험 (데이터를 바꿈)
cancel_order("O000902")       # 주문을 취소! 되돌리기 어려움
refund("O000902")             # 환불 실행! 돈이 나감

지금까지 우리 도구는 모두 읽기였습니다(조회). 그래서 안전했죠 — 잘못 호출해도 데이터가 안 바뀌니까요. 하지만 "환불 실행", "주문 취소" 같은 쓰기 도구는 신중해야 합니다. 잘못 실행하면 진짜 돈이 나가고, 되돌리기 어렵거든요.

이 강의 도구(policy_search, get_order_status, get_stock)는 모두 읽기 전용입니다. 의도적으로요. 쓰기 도구의 위험성과 안전장치는 08번에서 따로 다룹니다.

6. 읽기 vs 쓰기 — 멱등성

읽기와 쓰기의 핵심 차이는 멱등성(idempotent) 입니다.

읽기: 같은 호출을 여러 번 해도 결과·상태 동일 (멱등)
      get_order_status("O") 10번 = 1번 (데이터 안 바뀜)

쓰기: 호출할 때마다 상태가 바뀜 (비멱등)
      cancel_order("O") 10번 = 위험 (중복 취소? 오류?)

읽기는 몇 번 호출해도 안전하지만, 쓰기는 한 번 한 번이 영향을 줍니다. 그래서 에이전트가 실수로 쓰기 도구를 여러 번 부르면 큰일이죠. 이 차이를 이해하는 게 안전한 에이전트 설계의 기본입니다.

핵심 정리

  • 실전 도구 4원칙: 명확한 설명 · 입력 검증 · 결정적 반환 · 부작용 최소화.
  • 명확한 설명(입력 예시 포함)으로 라우팅 정확도 확보.
  • 입력 검증·예외 처리로 잘못된 입력에도 안 죽게.
  • 결정적 반환으로 재현성·디버깅·테스트 가능.
  • 읽기는 안전(멱등), 쓰기는 위험(비멱등) — 상태 변경은 신중히(08번).
