LLM은 함수를 직접 실행하지 못한다

한 줄 요약

이 강에서 가장 중요한 개념입니다. LLM은 우리 컴퓨터의 함수를 실행할 수 없습니다. 대신 "이 함수를, 이런 인자로 불러줘"라는 요청(JSON) 을 만들어 줄 뿐입니다. 실제 실행은 우리(파이썬) 가 합니다.

1. 가장 흔한 오해

많은 사람이 이렇게 상상합니다.

"LLM에게 함수를 주면, LLM이 그 함수를 실행해서 답을 주겠지?"

틀렸습니다. LLM은 텍스트(토큰)를 생성하는 기계일 뿐, 여러분의 컴퓨터에서 파이썬 코드를 돌릴 능력이 없습니다. LLM이 하는 일은 딱 하나입니다 — "어떤 함수를 어떤 인자로 부르면 좋겠다"는 결정을 알려 주는 것.

LLM이 만드는 것:  get_stock(product_name="이어버드")  ← 이건 '실행'이 아니라 '요청서'(JSON)
실제 실행:        우리가 그 요청서를 받아 파이썬으로 함수를 돌림

비유: LLM은 주문서를 쓰는 손님입니다. "아메리카노 한 잔, 샷 추가요"라고 주문서를 작성할 뿐, 직접 커피를 내리지는 않습니다. 커피를 내리는 건 바리스타(우리 파이썬 코드) 입니다.

2. Function Calling의 5단계

이 "결정 → 실행" 분리를 단계로 풀면 이렇습니다.

  1. 우리: 도구 목록(함수+설명)을 모델에 알려줌 + 질문.
  2. 모델(LLM): "get_stock(product_name='이어버드')를 호출하면 되겠다"고 JSON으로 알려줌. (여기까지가 모델의 일 — 모델은 실행을 못 한다!)
  3. 우리: 그 함수를 실제로 실행 → "재고 225개" 결과를 얻음.
  4. 우리: 결과를 다시 모델에 전달.
  5. 모델(LLM): 결과를 보고 사람 말로 최종 답변 작성.

이 5단계가 Function Calling의 전부입니다. 자동이든 수동이든 이 흐름은 똑같습니다 — 다만 누가 3·4단계를 처리하느냐만 다릅니다(다음 절).

3. 왜 이렇게 나눠 놨을까?

"그냥 LLM이 실행까지 하면 편하잖아?"라고 생각할 수 있습니다. 하지만 이 분리에는 중요한 이유가 있습니다.

  • 보안: LLM이 우리 시스템의 함수를 마음대로 실행하면 위험합니다. "결정만" 받고 실행은 우리가 통제하면, 위험한 호출을 막을 수 있습니다(18강 쓰기 도구).
  • 제어: 실행 전에 인자를 검증하거나, 로그를 남기거나, 권한을 확인할 수 있습니다.
  • 유연성: 같은 "결정"을 받아 다르게 처리할 수 있습니다(재시도, 캐싱 등).

즉, "모델은 결정, 실행은 우리" 라는 구조가 안전하고 유연한 에이전트의 토대입니다.

4. 함수의 '설명서'가 핵심

LLM은 함수 본문(코드)을 볼 수 없습니다. 오직 함수 이름·독스트링·인자 타입만 보고 "이 도구를 써야겠다"를 판단합니다.

def get_stock(product_name: str) -> str:
    """상품명(일부만 입력해도 됨)을 받아 현재 재고 수량을 반환한다."""
    # 위 독스트링이 모델에게 주는 유일한 '사용 설명서'다.
    # product_name: str 처럼 인자 이름과 타입도 모델이 본다.
    ...

그래서 독스트링을 명확히 쓰는 것이 도구 성능을 좌우합니다. 이건 6강(도구 설계)에서 깊이 다룹니다.

핵심 정리

  • LLM은 함수를 실행하지 못한다 — "무엇을 부를지" 결정(JSON)만 만든다.
  • 실제 실행은 우리(파이썬) 가 한다 → "모델은 결정, 실행은 우리".
  • 이 분리는 보안·제어·유연성을 위한 것이다.
  • 모델은 함수의 이름·독스트링·타입만 보고 도구를 고른다.
  • 다음 절에서 이 5단계를 자동으로 돌리는 법과 수동으로 돌리는 법을 비교합니다.
