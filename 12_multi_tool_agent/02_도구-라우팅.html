도구 라우팅(Tool Routing)

한 줄 요약

도구 라우팅은 LLM이 각 도구의 docstring을 읽고 "지금 어떤 도구가 필요한가"를 스스로 판단하는 것입니다. 우리가 if-else로 분기를 짜는 게 아니라, LLM이 알아서 적절한 도구로 질문을 보냅니다.

1. 라우팅이란?

여러 도구가 있을 때, "이 질문에는 어떤 도구를 써야 하지?"를 정하는 게 라우팅입니다. ("라우팅"은 "길을 정해 보낸다"는 뜻으로, 우편물을 알맞은 부서로 보내는 것과 같습니다.)

"고객 주문 상태는?"     → get_order_status 로 라우팅
"P0025 재고 있어?"      → get_stock 로 라우팅
"이번 달 매출은?"        → run_pandas 로 라우팅

핵심은 이 라우팅을 우리가 코드로 짜지 않는다는 것입니다. LLM이 합니다.

2. if-else 라우팅의 문제

만약 우리가 직접 라우팅을 짠다면 이렇게 됩니다.

# 나쁜 방법 — if-else 하드코딩
if "주문" in question:
    get_order_status(...)
elif "재고" in question:
    get_stock(...)
elif "매출" in question:
    run_pandas(...)
# 표현이 조금만 달라도("배송 어디까지?", "물건 남았어?") 놓침!

6강에서 봤듯, 이 방식은 표현이 조금만 달라도 놓치고, 도구가 늘 때마다 if가 늘어납니다. 유지보수 지옥이죠.

3. LLM 라우팅 — docstring을 보고 판단

LLM 라우팅은 다릅니다. 각 도구의 docstring을 읽고 LLM이 의미를 이해해 고릅니다.

@tool
def get_order_status(customer_id: str) -> str:
    """고객 ID(예: 'C0001')의 가장 최근 주문 1건의 상태를 조회한다.
    상품명, product_id, 주문일, 상태를 반환한다."""
    # [라우팅 근거] 이 docstring을 LLM이 읽고 "주문 상태 질문엔 이 도구"라고 판단
    ...

그래서 "배송 어디까지 왔어?", "내 주문 상태?", "물건 언제 와?" 같은 다양한 표현도 LLM이 의미로 이해해 get_order_status로 보냅니다. if "주문" 같은 단어 매칭이 아니라 의미 이해니까요.

비유: if-else는 "주문이라는 단어가 있으면 1번 창구"라고 적힌 안내판입니다. LLM 라우팅은 손님 말을 알아듣고 "아, 배송 문의시군요. 3번 창구로 가세요"라고 안내하는 직원이죠. 표현이 달라도 의미를 이해합니다.

4. 라우팅의 흐름

질문: "C0001 주문 상태와 그 상품 재고는?" → LLM이 docstring들을 읽고 판단:

  1. "주문 상태" → get_order_status(customer_id='C0001') → 결과: "현미 잡곡, product_id=P0025"
  2. "그 상품 재고" → get_stock(product_id='P0025') (앞 결과를 이어 씀!) → 결과: "155개"
  3. 두 결과를 모아 답변

LLM이 질문을 분석해 두 도구를 순서대로 라우팅했고, 앞 결과(P0025)를 다음 도구에 넘겼습니다. 이게 멀티툴 에이전트의 핵심입니다.

5. 좋은 라우팅 = 좋은 docstring

라우팅 정확도는 docstring 품질에 달렸습니다(6강 복습).

  • 명확한 docstring: "고객 주문 상태 조회" → 정확한 라우팅
  • 모호한 docstring: "정보 조회" → 엉뚱한 도구 선택

그래서 멀티툴 에이전트를 만들 때는 각 도구의 docstring을 또렷하고 구별되게 쓰는 게 가장 중요합니다. 도구가 많아질수록 더 그렇습니다.

핵심 정리

  • 도구 라우팅 = LLM이 docstring을 보고 적절한 도구를 스스로 고르는 것.
  • if-else 하드코딩은 표현 변화에 약하고 유지보수가 어렵다.
  • LLM 라우팅은 의미를 이해해 다양한 표현도 올바르게 보낸다.
  • 라우팅 정확도는 docstring 품질에 달렸다(6강).
