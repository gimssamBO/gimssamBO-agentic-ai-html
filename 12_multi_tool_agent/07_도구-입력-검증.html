도구 입력 검증/정규화

한 줄 요약

모델은 c1, 스마트 워치 처럼 형식이 어긋난 인자를 도구에 넘기기도 합니다. 도구 안에서 입력을 먼저 검증·정규화하면, 잘못된 조회로 빈 결과가 나는 일을 막습니다.

1. 모델은 입력을 헷갈린다

LLM은 똑똑하지만 인자를 항상 정확히 채우진 못합니다.

사용자: "c1 고객 주문 알려줘"
모델이 도구에 넘기는 인자: customer_id='c1'   ← 소문자, 자릿수 부족!
실제 데이터 형식: 'C0001'                      ← 대문자 C + 4자리

→ orders[orders['customer_id'] == 'c1'] → 빈 결과!

c1은 형식이 틀렸습니다(소문자, 4자리 아님). 이대로 조회하면 "주문 없음"이 나오죠. 하지만 진짜 문제는 "고객이 없는 게 아니라 입력 형식이 틀린 것" 입니다. 이 둘을 구분해야 제대로 안내할 수 있습니다.

2. 검증/정규화 헬퍼

입력을 검사하고 다듬는 헬퍼를 만듭니다. (실습 파일: sections/12_multi_tool_agent/07_도구-입력-검증.py)

import re

# 고객ID 형식: 대문자 C + 숫자 4자리 (예: C0001)
CUSTOMER_ID_RE = re.compile(r"^C\d{4}$")

def validate_customer_id(customer_id: str):
    """고객ID를 정규화(공백 제거·대문자화)하고 'C+4자리' 형식을 검사한다.
    반환: (정규화된_ID, 오류문자열). 오류가 없으면 오류문자열은 None."""
    cid = (customer_id or "").strip().upper()    # ① 정규화: 공백 제거 + 대문자
    if not CUSTOMER_ID_RE.match(cid):            # ② 검증: 형식 검사
        return None, (
            f"[입력오류] 고객ID '{customer_id}' 형식이 올바르지 않습니다. "
            f"'C' 다음 숫자 4자리(예: C0001) 형태로 입력해 주세요."
        )
    return cid, None

def normalize_product_name(name: str) -> str:
    """상품명의 양끝 공백 제거 + 연속 공백을 하나로 정리한다."""
    return re.sub(r"\s+", " ", (name or "").strip())

두 가지 일을 합니다.

  • 정규화(normalize): 고칠 수 있는 건 고침 (c1 → C1, 공백 제거)
  • 검증(validate): 못 고치는 건 오류로 (C1은 4자리가 아니므로 오류)

3. 정규화 vs 검증의 차이

둘은 다릅니다.

구분 하는 일 예시
정규화 자동으로 고침 ' c0156 ' → 'C0156'
검증 틀리면 거부 'c1' → "형식 오류" (4자리 아님)

정규화로 사소한 차이는 받아 주고(소문자·공백), 검증으로 명백한 오류는 거부합니다(자릿수 부족). 이러면 사용자 입력이 조금 지저분해도 관대하게 처리하면서, 진짜 잘못된 입력은 걸러냅니다.

비유: 입국 심사와 같습니다. 여권 사진의 옷차림(공백·대소문자)은 문제 삼지 않지만(정규화), 여권 번호 자릿수가 틀리면(검증) 통과시키지 않죠.

4. 도구 안에서 검증 적용

@tool 함수 안에서 조회 전에 검증합니다.

@tool
def get_order_status(customer_id: str) -> str:
    """고객 ID(예: 'C0001')의 가장 최근 주문 상태를 조회한다."""
    cid, err = validate_customer_id(customer_id)   # 조회 전에 형식부터 검증
    if err:
        return err          # 형식 위반 → 친절한 오류 문자열 반환
    df = orders[orders["customer_id"] == cid]      # 정규화된 cid로 조회
    if df.empty:
        return f"[조회실패] {cid} 고객의 주문 내역이 없습니다."
    ...

검증을 맨 앞에 둡니다. 형식이 틀리면 조회조차 하지 않고 바로 안내하죠. 정규화된 cid(대문자·공백 제거)로 조회하니, ' c0156 ' 같은 지저분한 입력도 잘 처리됩니다.

5. 실행 — 검증 동작 확인

# 헬퍼 단위 테스트
samples = ["C0001", "c1", " C0156 ", "X0001", ""]
for s in samples:
    cid, err = validate_customer_id(s)
    print(f"입력 {s!r:>10} -> 정규화 {cid!r} / 오류: {err}")

예상 출력

입력    'C0001' -> 정규화 'C0001' / 오류: None         ← 정상
입력       'c1' -> 정규화 None    / 오류: [입력오류]...  ← 4자리 아님
입력  ' C0156 ' -> 정규화 'C0156' / 오류: None         ← 공백 제거됨 (정상)
입력    'X0001' -> 정규화 None    / 오류: [입력오류]...  ← C로 시작 안 함
입력         '' -> 정규화 None    / 오류: [입력오류]...  ← 빈 값
  • C0001: 정상 통과
  • c1: 4자리가 아니라 오류 (정규화로 대문자는 됐지만 검증 실패)
  • C0156: 공백 제거되어 정상 통과 (정규화의 효과)
  • X0001, ``: 형식 오류

검증과 정규화가 함께 작동하는 게 보이죠.

6. 폴백과의 조합

06번의 폴백과 07번의 검증을 합치면, 실패 상황을 더 정확히 구분할 수 있습니다.

입력오류 ([입력오류]): "형식이 틀렸어요. C0001 형태로 입력해 주세요"   ← 07번 검증
조회실패 ([조회실패]): "형식은 맞는데 그런 고객이 없어요"              ← 06번 폴백

"고객이 없는 것"과 "입력이 틀린 것"은 다릅니다. 검증이 있으면 이 둘을 구분해 더 정확한 안내를 할 수 있죠. 둘 다 갖추면 견고한 에이전트가 됩니다.

핵심 정리

  • 모델은 형식이 어긋난 인자(c1, 공백)를 넘기기도 한다.
  • 정규화(자동으로 고침) + 검증(틀리면 거부)을 도구 앞에서 한다.
  • 정규화로 사소한 차이는 관대하게, 검증으로 명백한 오류는 거부.
  • 검증([입력오류])과 폴백([조회실패])을 구분하면 더 정확한 안내.
