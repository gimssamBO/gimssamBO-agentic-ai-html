대화 기록 누적과 토큰 관리

한 줄 요약

ReAct 루프는 매 스텝마다 관찰 결과를 history에 덧붙이므로, 메시지와 토큰이 계속 불어납니다. 토큰은 곧 비용·지연이므로, 오래된 기록을 잘라내는 트리밍(trimming) 이 필요합니다. 단, 첫 질문(목표)은 반드시 보존해야 합니다.

1. 왜 토큰이 계속 늘어나는가

ReAct 루프는 매 스텝마다 history에 두 개씩 메시지를 추가합니다 — 모델의 도구 호출 + 우리의 실행 결과. 그리고 매번 모델을 호출할 때 history 전체를 넘깁니다.

STEP 1: history = [질문]                      → 토큰 적음
STEP 2: history = [질문, 호출1, 결과1]          → 토큰 늘어남
STEP 3: history = [질문, 호출1, 결과1, 호출2, 결과2] → 더 늘어남
...

스텝이 진행될수록 history가 길어지고, 매 호출의 입력 토큰이 선형으로 증가합니다. 긴 대화나 많은 스텝에서는 이게 비용 폭탄이 됩니다.

비유: 회의가 길어질수록 "지금까지 얘기 다시 정리하면…"을 매번 반복하면, 회의가 길어질수록 정리 시간이 점점 더 들죠. history도 마찬가지입니다.

2. 토큰 증가를 눈으로 보기

usage_metadata로 매 스텝의 토큰을 출력하면 증가가 보입니다. (실습 파일: sections/07_agent_loop/07_대화기록-누적과-토큰-관리.py)

for step in range(1, max_steps + 1):
    resp = client.models.generate_content(model=GEMINI_MODEL, contents=history, config=config)

    um = resp.usage_metadata
    print(f"[STEP {step}] history {len(history)}개 | "
          f"입력 {um.prompt_token_count} + 출력 {um.candidates_token_count} "
          f"= 누적 {um.total_token_count} 토큰")

    if not resp.function_calls:
        break
    # ... history.append(...) 로 기록 추가 ...

예상 출력

[STEP 1] history 1개 | 입력 120 + 출력 18 = 누적 138 토큰
[STEP 2] history 3개 | 입력 185 + 출력 20 = 누적 205 토큰   ← 입력 토큰 늘어남
[STEP 3] history 5개 | 입력 250 + 출력 45 = 누적 295 토큰   ← 더 늘어남

history 개수가 늘면서 입력 토큰(prompt_token_count)이 계속 증가하는 게 보입니다.

3. 해결책 — 트리밍(trimming)

오래된 중간 기록은 대개 최종 판단에 덜 중요합니다. 그래서 최근 몇 개만 남기고 잘라냅니다. 단, 한 가지 절대 규칙이 있습니다.

첫 질문(원래 목표)은 반드시 보존한다. 이게 사라지면 모델이 "내가 무슨 일을 하던 중이었지?"를 잊어버립니다.

def trim_history(history, keep: int = 4):
    """시스템/첫 사용자 메시지는 보존하고 '최근 keep개'만 유지한다."""
    if len(history) <= keep + 1:
        return history                  # 자를 게 없으면 그대로
    head = history[:1]                  # 첫 사용자 메시지(원래 목표) 보존
    tail = history[-keep:]              # 최근 keep개만 유지
    return head + tail

head(첫 질문) + tail(최근 N개)를 합쳐 돌려줍니다. 가운데의 오래된 관찰들은 버리는 거죠.

4. 트리밍 적용

print(f"트리밍 전: {len(history)}개")
trimmed = trim_history(history, keep=2)
print(f"트리밍 후: {len(trimmed)}개 (첫 질문 + 최근 2개 보존)")
# → 다음 호출부터 입력 토큰이 줄어 비용·지연 감소

예상 출력

트리밍 전: 5개
트리밍 후: 3개 (첫 질문 + 최근 2개 보존)

5개에서 3개로 줄었습니다. 다음 모델 호출부터는 입력 토큰이 줄어 비용과 지연이 감소합니다.

5. 트리밍의 트레이드오프

트리밍은 공짜가 아닙니다. 잘라낸 정보는 모델이 못 봅니다.

  • 너무 많이 자르면: 모델이 중요한 중간 관찰을 잊어 잘못 판단할 수 있음.
  • 너무 적게 자르면: 토큰 절감 효과가 작음.
  • 적절히: 최근 몇 스텝 + 첫 질문을 남기는 게 보통 안전.

더 정교한 방법으로는 오래된 대화를 요약해서 압축하는 기법도 있습니다(19강 메모리에서 다룹니다). 트리밍은 "버리기", 요약은 "압축하기"인 셈이죠.

6. 비용 감각 정리 (2강 복습)

2강에서 "토큰 = 비용"이라고 배웠습니다. ReAct 루프에서 이게 현실이 됩니다.

  • 스텝이 많을수록 → history가 길어짐 → 입력 토큰↑ → 비용↑
  • 그래서 트리밍(이 절) + 반복 방지(06번) + max_steps(03번)로 비용을 통제
  • 이 세 가지가 비용 효율적인 에이전트의 기본기

핵심 정리

  • ReAct 루프는 history가 쌓여 입력 토큰이 선형 증가한다(비용·지연↑).
  • usage_metadata로 토큰 증가를 직접 확인할 수 있다.
  • 트리밍(trim_history)으로 오래된 기록을 잘라 토큰을 줄인다.
  • 단, 첫 질문(목표)은 반드시 보존한다.
  • 더 정교하게는 요약 압축(19강)을 쓴다.
