[신규] 조건부 분기로 품질 재검토

한 줄 요약

지금까지의 파이프라인은 한 방향 일직선이었습니다. 여기에 검수(check) 노드와 갈림길(add_conditional_edges) 을 더해, 분석이 부실하면 다시 조사(루프), 충분하면 작성으로 진행하게 만듭니다. 무한루프를 막도록 재시도 횟수를 상태에 두고 최대 2회로 제한합니다. 여기서 비로소 "왜 그래프인가" 가 드러납니다.

실습 파일: sections/27_ai_team/06_조건부-분기로-품질-재검토.py

1. 일직선의 한계 — 부실해도 그냥 통과

05번 파이프라인은 분석이 좋든 나쁘든 무조건 Writer로 넘어갑니다.

researcher → analyst → writer (분석이 부실해도 그대로 보고서行)

분석이 두 줄밖에 안 나오거나 강점·약점이 빠져도, Writer는 그 부실한 분석으로 보고서를 씁니다. "분석이 별로면 다시 조사하라" 는 판단이 없죠. 이걸 더하려면 갈림길이 필요합니다.

2. 목표 흐름 — 검수 후 갈림길

researcher → analyst → check 에서 갈립니다.

  • (부실 & 재시도 여유) → redo → analyst …(루프)

  • (충분 or 한도 초과) → writer → END

  • check(검수): 분석 품질을 평가해 충분/부실 판정.

  • 부실 + 재시도 여유 → redo(재조사)로 갔다가 다시 analyst로 (루프).
  • 충분 or 재시도 한도 초과 → writer로 진행.

이 "갈림길 + 되돌아가기"는 for/if로 짜면 엉키지만, 그래프에선 엣지 한 줄로 선언됩니다.

3. 상태 확장 — 카운터와 판정 칸

기존 TeamState에 재시도 횟수와 판정을 담을 칸을 추가합니다.

from ch27_ai_team import (                  # 기존 노드·로더 그대로 재사용
    TeamState as BaseState,
    researcher, analyst, writer, load_competitor_text,
)

class TeamState(BaseState):     # 기존 상태를 상속해 칸 추가
    retries: int   # 재수집(루프) 횟수 — 무한루프 방지용 카운터
    verdict: str   # 검수 결과: '충분' | '부실'

MAX_RETRIES = 2    # [경고] 루프 상한 — 넘으면 부실해도 Writer로 강제 진행

retries(카운터) 가 핵심입니다. 루프를 돌 때마다 1씩 올려, 상한(2회) 에 닿으면 더 안 돌게 합니다. 무한루프를 막는 안전장치죠(7강 max_steps 정신).

4. 검수 노드 — 품질 평가

분석이 충분한지 규칙 기반으로 빠르게 거릅니다.

def check(state: TeamState) -> dict:
    """Analyst 산출물의 품질을 평가하는 검수 노드."""
    analysis = state.get("analysis", "")
    # 규칙 기반 1차 필터: 너무 짧거나 핵심 키워드가 없으면 '부실'
    too_short = len(analysis) < 200
    missing_core = not any(k in analysis for k in ("강점", "약점", "기회"))
    verdict = "부실" if (too_short or missing_core) else "충분"
    print(f"  [검수] 분석 길이={len(analysis)}자, "
          f"핵심키워드={'없음' if missing_core else '있음'} → 판정: {verdict}")
    return {"verdict": verdict}

여기선 길이(200자 미만) 와 핵심 키워드(강점/약점/기회) 유무로 판정합니다. LLM에게 평가시킬 수도 있지만(비용↑), 간단한 규칙으로도 1차 거르기엔 충분합니다. (25강 규칙 라우터의 정신 — 싸고 빠른 규칙 먼저.)

5. 라우터 — 갈림길의 방향 결정

검수 결과에 따라 다음에 갈 노드 이름을 문자열로 반환하는 함수입니다.

def route_after_check(state: TeamState) -> str:
    """검수 결과에 따라 다음 노드 이름을 반환. add_conditional_edges가 이 값으로 분기."""
    # [경고] 무한루프 방지: 재시도 상한에 도달하면 부실이어도 진행
    if state["verdict"] == "부실" and state["retries"] < MAX_RETRIES:
        return "redo"
    return "ok"

두 조건을 모두 봅니다: 부실이면서 아직 재시도 여유(retries < 2)가 있을 때만 redo. 둘 중 하나라도 아니면(충분이거나 한도 초과) ok. 이 함수가 갈림길의 판단입니다.

6. 재조사 노드 — 카운터 올리며 루프

def researcher_retry(state: TeamState) -> dict:
    """재수집 단계. 재시도 카운터를 올린 뒤 다시 사실을 정리한다."""
    n = state["retries"] + 1
    print(f"  [재수집] {n}회차 — 부실 판정으로 Researcher 재가동")
    upd = researcher({"raw": load_competitor_text()})  # 원천부터 다시 정리
    upd["retries"] = n                                  # 카운터 갱신
    return upd

원천 텍스트로 되돌려 researcher를 다시 돌리고, retries를 +1 합니다. 이 카운터 갱신이 없으면 무한루프에 빠지니 반드시 올려야 합니다.

7. 조건부 엣지로 그래프 조립

핵심은 add_conditional_edges입니다.

def build_team():
    g = StateGraph(TeamState)
    g.add_node("researcher", researcher)
    g.add_node("analyst", analyst)
    g.add_node("check", check)
    g.add_node("redo", researcher_retry)   # 재수집 노드(루프 경로)
    g.add_node("writer", writer)

    g.add_edge(START, "researcher")
    g.add_edge("researcher", "analyst")
    g.add_edge("analyst", "check")         # 분석 다음엔 반드시 검수
    # [핵심] 검수 후 갈림길: 라우터 반환값 → 실제 노드 매핑
    g.add_conditional_edges(
        "check",
        route_after_check,                 # 이 함수가 "redo"/"ok" 반환
        {"redo": "redo", "ok": "writer"},  # 반환값 → 갈 노드
    )
    g.add_edge("redo", "analyst")          # 재수집 후 다시 분석 → 다시 검수(루프!)
    g.add_edge("writer", END)
    return g.compile()

add_conditional_edges(노드, 라우터함수, 매핑):

check 노드 끝 → route_after_check(state) 호출 → "redo" 또는 "ok" 반환
   "redo" → redo 노드로
   "ok"   → writer 노드로

그리고 redo → analyst 엣지가 루프를 만듭니다: analyst → check → redo → analyst → check → ... 가 검수를 통과하거나 한도에 닿을 때까지 돕니다.

8. 실행과 결과

if __name__ == "__main__":
    team = build_team()
    initial = {"raw": load_competitor_text(), "analysis": "", "report": "",
               "retries": 0, "verdict": ""}        # 카운터·판정 칸도 초기화
    final = initial
    for state in team.stream(initial, stream_mode="values"):
        final = state
    print(f"\n최종 재시도 횟수: {final['retries']}회 / 최종 판정: {final['verdict']}")
    print(final["report"])

예상 출력

  [검수] 분석 길이=512자, 핵심키워드=있음 → 판정: 충분

최종 재시도 횟수: 0회 / 최종 판정: 충분
# 승승장구몰 경쟁사 분석 리포트 ...

분석이 충분하면 재시도 0회로 바로 통과합니다. 만약 부실했다면 [재수집] 1회차 ...가 찍히며 루프를 돌고, 그래도 안 되면 2회에서 멈춰 강제 진행하죠.

9. 여기서 드러나는 "왜 그래프인가"

[for/if 로 짰다면]
   while + 카운터 + 분기 조건이 main 코드에 뒤엉킴 → 흐름이 안 보임

[StateGraph]
   check·redo·writer는 각자 함수, 흐름은 build_team()의 엣지에 '그림'으로 선언
   → "검수 후 부실이면 redo로 돌고, 아니면 writer로" 가 한눈에 보임

되돌아가기·반복·조건 분기 — 바로 이때 StateGraph의 진가가 나옵니다. 일직선이면 for로 충분했지만, 갈림길이 생기니 그래프가 흐름을 훨씬 명확하게 표현합니다.

핵심 정리

  • 일직선 파이프라인에 검수 노드 + 조건부 분기를 더해 품질 재검토 루프를 만듦.
  • add_conditional_edges(노드, 라우터, 매핑): 라우터 반환값으로 다음 노드를 선택.
  • redo → analyst 엣지가 루프를 형성, retries 카운터 + MAX_RETRIES로 무한루프 방지.
  • 검수는 규칙 기반(길이·키워드)으로 싸고 빠르게 1차 거르기.
  • 되돌아가기·반복이 생길 때 StateGraph의 진가가 드러난다.
