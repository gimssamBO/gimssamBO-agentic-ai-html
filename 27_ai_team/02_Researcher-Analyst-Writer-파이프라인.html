Researcher → Analyst → Writer 파이프라인

한 줄 요약

AI 팀은 역할이 다른 세 에이전트가 공유 문서(State) 를 차례로 채워 가는 파이프라인입니다. Researcher가 사실을 정리하면, Analyst가 그것으로 분석하고, Writer가 보고서로 다듬습니다. 각 역할은 앞 단계 산출물만 입력으로 받습니다.

1. 세 역할

승승장구몰 경쟁사 분석을 예로, 세 명이 분업합니다.

competitor_data.csv(원천 데이터) → Researcher(사실만 정리, 해석 금지) → Analyst(강점·약점·기회 분석) → Writer(보고서로 변환) → 마크다운 리포트(최종)

  • Researcher(리서처) — 원천 데이터를 읽어 사실만 항목별로 정리합니다. 해석은 하지 않습니다.
  • Analyst(분석가) — 정리된 사실로 경쟁사별 강점·약점과 승승장구몰의 기회를 분석합니다.
  • Writer(작성자) — 분석 결과를 임원 보고용 마크다운 리포트(제목·요약·정리·결론)로 변환합니다.

2. 왜 역할을 나누나 — 25·26강의 연장선

"경쟁사 분석 리포트 만들어줘"를 한 번의 LLM 호출로 시키면 어떨까요?

[한 번에 다]
   → 사실·분석·서술이 뒤섞여, 근거가 약하거나 형식이 들쭉날쭉
   → "분석이 부실한데 글만 그럴듯한" 보고서가 나오기 쉬움

[역할 분리]
   → Researcher가 사실을 탄탄히 → Analyst가 그 위에서 깊이 분석
   → Writer는 잘 정리된 분석만 글로 → 각 단계 품질이 안정적

각 역할이 자기 일에만 집중하니 품질이 고릅니다. 25강(전문가 팀), 26강(Planner/Worker)에서 배운 "나눠서 각자 잘하는 일에 집중" 원칙을 파이프라인으로 적용한 것입니다.

3. 핵심 — "앞 단계 산출물만" 입력으로

이 파이프라인의 중요한 성질은 각 역할이 앞 단계의 결과만 본다는 것입니다.

Researcher:  원천 데이터        → 정리된 사실
Analyst:     정리된 사실         → 분석   (원천 데이터는 안 봄)
Writer:      분석               → 리포트 (정리된 사실·원천은 안 봄)

이렇게 단계가 분리(느슨한 결합) 되어 있어 좋은 점:

  • 품질 안정 — 각 단계 입력이 명확해, 앞 단계가 잘하면 뒤 단계도 잘합니다.
  • 교체 용이 — Analyst만 더 똑똑한 모델로 바꿔도, 인터페이스(사실 입력 → 분석 출력)가 같으면 됩니다.
  • 디버깅 용이 — 결과가 이상하면 어느 단계에서 틀렸는지 추적하기 쉽습니다.

4. 파이프라인 vs 26강 오케스트레이터

26강과 비슷하지만 결정적 차이가 있습니다.

[26강 Planner/Worker]
   Planner가 작업을 '여러 개로 쪼개고' → Worker가 각각 '독립' 수행 → 취합
   (작업끼리 서로 무관, 병렬 가능)

[27강 파이프라인]
   Researcher → Analyst → Writer 가 '한 줄로 이어짐'
   (앞 결과가 뒤 입력 = 순서가 중요, 직렬)

26강 Worker들은 서로 독립이라 순서가 상관없었지만(병렬 가능), 27강 세 역할은 앞 결과를 뒤가 받으므로 순서가 핵심입니다. 이런 직렬 의존 흐름을 깔끔히 표현하는 도구가 바로 다음 절의 StateGraph입니다.

5. 도구를 안 쓰는 이유

이번 세 역할은 외부 도구(검색·DB조회)를 쓰지 않고 입력 텍스트를 가공만 합니다. 그래서 create_agent(도구 쓰는 에이전트) 대신, 노드 안에서 llm.invoke(...) 만 하면 됩니다.

- 도구가 필요 없음 → 단순 LLM 호출로 충분
- 핵심은 '흐름을 StateGraph로 선언'하는 것
- (도구가 필요하면 노드 안에서 create_agent를 불러도 됨)

즉 이번 강의 초점은 에이전트의 똑똑함이 아니라 여러 에이전트를 어떻게 잇는가(오케스트레이션) 입니다.

핵심 정리

  • AI 팀 = Researcher(사실) → Analyst(분석) → Writer(보고서) 직렬 파이프라인.
  • 각 역할은 앞 단계 산출물만 입력으로 받음 → 느슨한 결합·품질 안정·교체 용이.
  • 26강 Worker는 독립(병렬 가능), 27강 세 역할은 직렬 의존(순서가 핵심).
  • 도구를 안 쓰므로 노드는 단순 llm.invoke — 초점은 "어떻게 잇는가".
  • 다음 절에서 이 흐름을 담는 공유 상태(State)와 그래프 구성요소를 봅니다.
