아키텍처와 인터페이스 설계 (4·5단계)

한 줄 요약

설계의 마지막 두 단계입니다. 4단계 아키텍처 — 확정한 구성요소들이 어떻게 연결되는지 전체 그림을 그립니다. 5단계 인터페이스 — 에이전트를 서비스로 쓰기 위한 외부 계약(진입 함수·세션·엔드포인트·실패 대비)을 정합니다.

1. 4단계 — 아키텍처 다이어그램

3단계에서 확정한 구성요소(도구 4개 + RAG + 단기메모리)가 어떻게 흐르는지 그림으로 그립니다.

위에서 아래로 흐릅니다.

  1. config.yaml + .env(키) → 설정/로깅 로더(29강)
  2. 사용자(질문) + thread_id → create_agent(prompt: 역할/규칙)
  3. 에이전트가 아래 구성요소를 골라 사용:
구성요소 데이터 소스
get_order_status orders.csv
get_stock inventory.csv
search_faq faq.csv
policy_search FAISS (정책 PDF)
InMemorySaver thread_id별 대화 기억
  1. → 최종 답변 → (선택) FastAPI: POST /chat {thread_id, message} (29강)

이 그림이 30강에서 구현할 시스템의 청사진입니다. 읽는 법:

  • 위에서 아래로: 설정 로드 → 에이전트 생성 → 도구/RAG 실행 → 답변.
  • 가운데 create_agent 가 지휘자: 질문을 보고 어떤 도구/RAG를 쓸지 LLM이 결정(5강 함수 호출).
  • 각 도구는 자기 데이터 소스로 연결: 주문은 orders.csv, 정책은 FAISS 인덱스.
  • InMemorySaver: thread_id 별로 대화를 기억(19강).

2. 아키텍처가 보여주는 것

좋은 아키텍처 그림은 한눈에 답을 줍니다.

- 데이터가 어디서 와서 어디로 가나?  (orders.csv → 도구 → 답변)
- 각 구성요소의 책임은?             (도구=조회, RAG=문서검색, 메모리=맥락)
- 어디가 외부와 만나나?             (위: 설정, 아래: FastAPI 엔드포인트)
- 무엇이 무엇에 의존하나?           (도구는 CSV에, policy_search는 FAISS에)

코드를 짜기 전에 이 그림으로 팀과 합의하고, 빠진 게 없는지 점검합니다. 그림에서 안 보이는 흐름은 코드에서도 엉킵니다.

3. 5단계 — 인터페이스 설계 (외부 계약)

에이전트를 서비스로 쓰려면, 외부에서 어떻게 부를지 계약(인터페이스) 을 먼저 정합니다.

항목 설계 결정 이유
진입 함수 answer(message, thread_id) -> str 한 줄로 호출 가능한 단일 진입점
세션 식별 thread_id(사용자/대화 단위) 메모리 격리(멀티 사용자)
상태 저장 InMemorySaver(데모) / 운영은 DB·Redis 프로세스 재시작 대비
엔드포인트 POST /chat {thread_id, message} 무상태 HTTP, 세션은 thread_id로
설정 config.yaml + .env 분리 코드 수정 없이 환경 전환
실패 대비 타임아웃·재시도·폴백 메시지 LLM/네트워크 불안정(29강)
비용·지연 모델 선택·프롬프트 길이·캐싱 무료티어 한도·응답속도

4. 핵심 결정 — 단일 진입점 answer()

가장 중요한 인터페이스 결정입니다.

def answer(message: str, thread_id: str = "demo") -> str:
    """외부에 노출되는 단일 진입점. thread_id로 대화 세션을 구분한다."""
    ...

왜 단일 진입점인가?

[잘된 설계]   에이전트 본체 = 순수 함수 answer()
              FastAPI 웹 계층 = answer()를 부르는 '얇은 래퍼'
              → 테스트(함수 직접 호출)·재사용·배포가 쉬움

[잘못된 설계] 웹 핸들러 안에 에이전트 로직이 다 들어감
              → 테스트하려면 서버를 띄워야 하고, 재사용 불가

에이전트 본체는 순수 함수로 만들고, FastAPI 같은 웹 계층은 이 함수를 부르는 얇은 껍데기로 둡니다(29강). 그래야 answer("안녕")처럼 함수만 따로 테스트할 수 있죠.

5. 세션 격리 — thread_id

answer("환불 규정?", thread_id="user_123")
answer("아까 그거 다시", thread_id="user_123")   # 같은 thread → 맥락 이어짐
answer("안녕하세요", thread_id="user_456")        # 다른 thread → 별개 대화

thread_id로 사용자/대화를 격리합니다. 같은 thread_id는 같은 대화로 묶여 "아까 그거"가 통하고(R5), 다른 thread_id는 서로 영향을 안 줍니다. 여러 사용자가 동시에 써도 대화가 안 섞이죠(19강 메모리).

6. 설계 단계에서 미리 챙기는 운영 고려사항

5단계에서 비용·지연·실패까지 미리 정해둡니다(상세 구현은 29강).

- 실패 대비: LLM 호출이 타임아웃/rate limit 나면? → 재시도 + 폴백 메시지
- 비용:      호출당 토큰·모델 선택 → 무료티어 한도 안에서
- 지연:      프롬프트가 너무 길면 느림 → 간결하게 + (반복 질문) 캐싱
- 설정 분리: config.yaml(공개 설정) + .env(비밀 키) → 코드 안 고치고 환경 전환

이걸 설계 단계에서 명시해두면, 구현할 때 "아 이것도 해야 하네"로 허둥대지 않습니다. 운영의 절반은 설계에서 결정됩니다.

핵심 정리

  • 4단계(아키텍처): 확정한 구성요소가 어떻게 연결·흐르는지 전체 그림으로 그린다 — 30강 청사진.
  • 5단계(인터페이스): 외부 계약을 정한다 — 진입 함수·세션·엔드포인트·설정·실패·비용.
  • 핵심 결정: 단일 진입점 answer(message, thread_id) — 본체는 순수 함수, 웹은 얇은 래퍼.
  • thread_id로 세션 격리(멀티 사용자 대화가 안 섞임).
  • 비용·지연·실패 대비를 설계 단계에서 미리 명시(구현은 29강).
  • 다음 절에서 이 설계를 코드 스켈레톤으로 박제합니다.
