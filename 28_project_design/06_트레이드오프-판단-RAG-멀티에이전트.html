[신규] 트레이드오프 판단 (RAG·멀티에이전트 도입 기준)

한 줄 요약

03번에서 "구성요소를 기준으로 판단한다"를 배웠습니다. 이걸 규칙으로 자동화한 설계 도우미를 만듭니다. 입력 신호(도구 수·사내문서·실시간데이터·멀티턴·역할 수)를 점수화해, RAG·장기메모리·멀티에이전트·워크플로우의 도입 여부를 근거와 함께 추천합니다. LLM 없이 경험칙(규칙) 만으로요.

실습 파일: sections/28_project_design/06_트레이드오프-판단-RAG-멀티에이전트.py

1. 왜 규칙으로 자동화하나

03번의 판단은 사람이 표를 보고 직접 했습니다. 그런데 프로젝트가 여러 개라면? 매번 "이건 RAG 필요할까?"를 고민하는 대신, 판단 기준을 코드로 박아두면 일관되게 추천받을 수 있습니다.

[매번 사람이 판단]   프로젝트마다 기준이 흔들림 → "지난번엔 왜 RAG 넣었지?"
[규칙으로 자동화]    같은 입력 → 같은 추천 + 근거 → 일관성·재현성

왜 LLM이 아니라 규칙? 설계 초반 의사결정은 LLM 없이도 경험칙(규칙) 으로 충분히 잡힙니다. "사내문서 있으면 RAG", "역할 3개+면 멀티에이전트" 같은 건 명확한 규칙이죠. 매번 LLM에 묻는 건 비용·불일치만 늘립니다. (25강 규칙 라우터의 정신.)

2. 설계 입력 명세

판단에 필요한 신호를 dataclass로 정의합니다(28강 AgentSpec 스타일).

from dataclasses import dataclass

@dataclass
class DesignSpec:
    """설계 판단에 필요한 입력 신호."""
    name: str = "이름없는 에이전트"
    num_tools: int = 0               # 붙일 도구 개수
    has_internal_docs: bool = False  # 사내문서(정책·매뉴얼 PDF 등) 유무
    needs_realtime: bool = False     # 실시간 데이터(주문·재고) 필요 여부
    multi_turn: bool = False         # 멀티턴(대화 맥락 유지) 필요 여부
    num_roles: int = 1               # 분리할 역할 수(리서처/분석가/작성자 등)
    long_running: bool = False       # 장기 누적 기억(사용자별 프로필) 필요 여부

이 7개 신호만 입력하면, 도우미가 구성요소 도입 여부를 추천합니다.

3. 판단 로직 — 점수와 근거

각 구성요소를 점수로 평가하고, 임계값을 넘으면 "도입"으로 추천합니다. 핵심은 근거를 함께 남기는 것입니다.

def decide(spec: DesignSpec) -> dict:
    """입력 신호를 규칙·점수로 평가해 구성요소 도입 여부와 근거를 반환한다."""
    result = {}

    # --- RAG: 사내문서가 있으면 강하게 권장 ---
    rag_score, rag_reasons = 0, []
    if spec.has_internal_docs:
        rag_score += 2
        rag_reasons.append("사내문서 보유 → 근거 있는 답변 위해 RAG 필요")
    if spec.needs_realtime:
        rag_reasons.append("단, 실시간 데이터는 RAG가 아니라 도구로 조회")
    result["RAG"] = {"도입": rag_score >= 2, "점수": rag_score,
                     "근거": " / ".join(rag_reasons) or "검색할 고정 문서가 없어 불필요"}

    # --- 장기메모리: 멀티턴 + 장기누적이면 권장 ---
    mem_score, mem_reasons = 0, []
    if spec.multi_turn:
        mem_score += 1
        mem_reasons.append("멀티턴 → 최소 단기메모리(thread_id) 필요")
    if spec.long_running:
        mem_score += 2
        mem_reasons.append("사용자별 장기 누적 → 장기메모리(프로필 저장) 권장")
    result["장기메모리"] = {"도입": mem_score >= 2, "점수": mem_score,
                          "근거": " / ".join(mem_reasons) or "단발성 대화라 메모리 불필요"}

    # --- 멀티에이전트: 역할 수·도구 수가 많으면 권장 ---
    ma_score, ma_reasons = 0, []
    if spec.num_roles >= 3:
        ma_score += 2
        ma_reasons.append(f"역할 {spec.num_roles}개 → 역할별 에이전트 분리 권장")
    if spec.num_tools >= 8:
        ma_score += 1
        ma_reasons.append(f"도구 {spec.num_tools}개 → 단일 에이전트엔 과부하")
    result["멀티에이전트"] = {"도입": ma_score >= 2, "점수": ma_score,
                           "근거": " / ".join(ma_reasons) or "역할·도구가 적어 단일로 시작"}

    # --- 워크플로우(StateGraph): 역할이 정해진 순서로 흐르면 권장 ---
    wf_score, wf_reasons = 0, []
    if spec.num_roles >= 2:
        wf_score += 2
        wf_reasons.append(f"역할 {spec.num_roles}개의 정해진 처리 순서 → 워크플로우로 명시")
    result["워크플로우"] = {"도입": wf_score >= 2, "점수": wf_score,
                         "근거": " / ".join(wf_reasons) or "단일 역할이라 선형 호출로 충분"}
    return result

설계 포인트

  • 각 구성요소가 자기 규칙으로 점수를 매김(사내문서 → RAG +2, 역할 3개+ → 멀티에이전트 +2).
  • 임계값(>= 2)을 넘으면 도입 추천.
  • 근거를 항상 반환 — "왜 도입/보류인지"가 남아야 신뢰할 수 있는 추천.
  • RAG 규칙에 "실시간은 RAG 아님(도구)" 주의를 넣어, 03번의 헷갈리는 구분을 자동으로 짚어줌.

4. 출력과 실행

추천 결과를 보기 좋게 출력합니다.

def print_decision(spec: DesignSpec) -> None:
    print("=" * 60)
    print(f"[시나리오] {spec.name}")
    print(f"  도구={spec.num_tools}개, 사내문서={spec.has_internal_docs}, "
          f"실시간={spec.needs_realtime}, 멀티턴={spec.multi_turn}, "
          f"역할={spec.num_roles}개, 장기={spec.long_running}")
    print("-" * 60)
    for i, (comp, d) in enumerate(decide(spec).items(), 1):
        mark = "도입 ✅" if d["도입"] else "보류 ⬜"
        print(f"[{i}] {comp:<7} {mark} (점수 {d['점수']}) — {d['근거']}")

5. 결과 읽기 — 케이스별 추천이 다르다

같은 도우미가 시나리오마다 다른 추천을 냅니다.

통합 CS 에이전트:  RAG ✅(사내문서) / 멀티에이전트 ⬜(도구 4개) → 28강 설계와 일치!
시장조사 팀:       RAG ⬜ / 멀티에이전트 ✅ + 워크플로우 ✅(역할 3개) → 27강 AI팀과 일치!
간단 FAQ 봇:       전부 ⬜ → 도구 1개로 충분, 과한 구성 불필요
VIP 개인비서:      RAG ✅ + 장기메모리 ✅(long_running) + 멀티에이전트 보류 → 균형

우리가 28강에서 손으로 내린 판단(RAG ✅, 멀티에이전트 ❌)을 규칙이 그대로 재현합니다. 즉 이 도우미는 03번의 판단 기준을 코드로 옮긴 것이고, 다른 프로젝트에도 일관되게 적용할 수 있습니다.

⚠️ 한계 — 이건 출발점이지 정답이 아닙니다. 규칙은 경험칙이라, 경계 사례(예: 도구 7개)에선 사람이 최종 판단해야 합니다. 도우미는 "생각의 체크리스트"로 쓰고, 결정은 사람이 내립니다.

핵심 정리

  • 03번의 구성요소 판단을 규칙 기반 도우미로 자동화(LLM 불필요, 경험칙).
  • DesignSpec(7개 신호) → decide()가 점수 + 근거로 RAG·메모리·멀티에이전트·워크플로우 추천.
  • 근거를 항상 함께 반환 → "왜 도입/보류"가 남아 신뢰 가능.
  • 시나리오마다 다른 추천 → 28강 손판단(RAG✅/멀티❌)을 규칙이 재현.
  • 규칙은 출발점, 경계 사례는 사람이 최종 판단.
  • 다음 절에서 28강을 정리합니다.
