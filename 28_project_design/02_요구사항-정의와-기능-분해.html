요구사항 정의와 기능 분해 (1·2단계)

한 줄 요약

설계의 첫 두 단계입니다. 1단계 요구사항 정의 — "무엇을 해결하나"를 사용자 시나리오로 적습니다. 2단계 기능 분해 — 각 요구사항을 함수 단위(입력/출력) 로 쪼갭니다. 막연한 "CS 봇 만들기"를 구체적인 함수 목록으로 바꾸는 과정입니다.

1. 1단계 — 요구사항 정의 (사용자 시나리오)

"무엇을 만들지"를 기능이 아니라 사용자가 실제로 하는 말로 적습니다. 승승장구몰 통합 CS 에이전트라면:

# 사용자 시나리오 필요한 능력
R1 "환불 절차 알려줘" 사내 정책 문서 검색(RAG)
R2 "내 주문 O000050 상태는?" 주문 DB 도구
R3 "이어버드 재고 있어?" 재고 도구
R4 "무료배송 기준?" FAQ 도구
R5 "아까 그 정책 다시 알려줘" 단기 메모리(대화 맥락)

왜 사용자 시나리오로 시작하나? "기능 목록"부터 적으면 만들기 쉬운 것 위주로 흐릅니다. 반면 사용자가 실제로 하는 말에서 출발하면, 진짜 필요한 능력이 드러나죠. R1~R5는 "고객이 상담창에 칠 법한 문장"이고, 각 문장이 곧 시스템이 갖춰야 할 능력을 가리킵니다.

1강에서 "LLM이 답 못 한 질문 2(주문 상태)"를 기억하시나요? 그게 바로 여기 R2입니다. 30강에서 드디어 이걸 풉니다.

2. 2단계 — 기능 분해 (요구사항 → 함수)

각 요구사항을 함수 단위로 쪼갭니다. 입력과 출력을 명시해, "무엇을 받아 무엇을 내는가"를 못박습니다.

get_order_status(order_id)  -> 주문 상태 문자열       (R2)
get_stock(product_name)     -> 재고 수량 문자열        (R3)
search_faq(keyword)         -> FAQ 답변               (R4)
policy_search(query)        -> 정책 문서 근거(RAG)     (R1)
+ 대화 thread_id 별 메모리                            (R5)

[요구사항]          →    [함수 (입력 → 출력)]
R1 정책 안내        →    policy_search(query) → 근거 텍스트
R2 주문 상태        →    get_order_status(order_id) → 상태 문자열
R3 재고 확인        →    get_stock(product_name) → 재고 문자열
R4 FAQ              →    search_faq(keyword) → 답변
R5 대화 기억        →    (함수 아님) thread_id 별 메모리로 처리

이건 백엔드의 유스케이스 분해와 똑같습니다. "주문 상태 알려줘"라는 추상적 요구를, get_order_status(order_id) -> str라는 구체적 계약으로 바꾸는 거죠.

3. 왜 입력/출력을 먼저 정하나

함수의 시그니처(이름·입력·출력) 를 먼저 정하면 좋은 점:

- 합의 고정: "주문 조회는 order_id를 받아 문자열을 낸다"가 못박힘
            → 구현자마다 제각각 만드는 일이 없음
- 도구화 준비: 5강에서 배운 @tool 은 함수의 시그니처·독스트링을 LLM이 읽음
            → 시그니처가 명확해야 LLM이 도구를 잘 고름
- 테스트 용이: 입출력이 정해져 있어, 구현 전에 테스트부터 짤 수 있음
- 병렬 작업: 팀이면 시그니처만 합의하고 각자 구현 가능

특히 에이전트에서는 이 함수들이 곧 도구(@tool) 가 됩니다. 시그니처와 독스트링이 명확해야 LLM이 "이 질문엔 이 도구"를 제대로 고르죠(6강 도구 설계 원칙).

4. 함수로 안 쪼개지는 것 — R5(메모리)

주의할 점: R5(대화 기억)는 함수가 아닙니다.

R1~R4: 입력 → 출력이 명확한 '함수(도구)'
R5:    "아까 그 정책" 을 이해하려면 → 대화 맥락을 유지하는 '메모리'

"아까 그거 다시 알려줘"는 특정 입력→출력 함수로 만들 수 없습니다. 이전 대화를 기억하는 장치(메모리) 가 필요하죠. 그래서 R5는 도구가 아니라 thread_id 별 단기 메모리(19강)로 처리합니다.

이렇게 요구사항을 분해하다 보면 "이건 도구, 저건 메모리, 그건 RAG" 가 자연스럽게 갈립니다. 그 판단을 체계적으로 하는 게 다음 절(3단계, 구성요소 필요성 판단)입니다.

5. 분해 결과 정리

지금까지의 결과를 모으면:

도구 4개:   get_order_status, get_stock, search_faq, policy_search
RAG:        policy_search 가 정책/멤버십 PDF를 검색 (R1)
메모리:     thread_id 별 단기 메모리 (R5)
멀티에이전트: ? (아직 판단 안 함 — 3단계에서)

요구사항 5개가 구체적인 구성요소 목록으로 바뀌었습니다. "CS 봇 만들기"라는 막연한 목표가, 이제 "도구 4개 + RAG + 메모리"라는 만들 수 있는 단위가 됐죠.

핵심 정리

  • 1단계(요구사항): "무엇을 해결하나"를 사용자 시나리오(R1~R5) 로 적는다 — 기능이 아니라 사용자의 말에서 출발.
  • 2단계(기능 분해): 각 요구사항을 함수(입력→출력) 로 쪼갠다 — 백엔드 유스케이스 분해와 동일.
  • 시그니처를 먼저 정하면 합의 고정·도구화·테스트·병렬작업에 유리.
  • R5(메모리) 는 함수로 안 쪼개짐 → thread_id 별 단기 메모리로 처리.
  • 다음 절에서 3단계 — 구성요소(도구·RAG·메모리·멀티에이전트) 필요성 판단을 다룹니다.
