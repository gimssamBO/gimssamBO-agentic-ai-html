바로 코딩이 망하는 이유

한 줄 요약

27강까지 도구·RAG·메모리·멀티에이전트를 따로따로 만들었습니다. 30강에선 이걸 하나의 서비스로 합칩니다. 그런데 설계 없이 바로 코드부터 짜면, 책임이 뒤섞이고 인터페이스가 불명확하며 비용·실패 대비가 빠진 결과가 나옵니다. 에이전트도 결국 하나의 백엔드 서비스 — 설계 → 구현 순서를 지켜야 합니다.

1. 이제 "합치는" 단계입니다

지금까지 배운 것들을 떠올려 봅시다.

5~12강:  도구(주문조회·재고·계산·검색)
13~18강: RAG(정책 문서 검색)
19~20강: 메모리(대화 맥락·사용자 기억)
21~27강: 워크플로우·멀티에이전트(협업)

각각은 따로 동작했습니다. 30강의 목표는 이걸 모아 "진짜로 일하는 승승장구몰 통합 CS 에이전트" 하나로 만드는 것입니다. 그런데 여기서 많은 사람이 실수합니다 — 곧장 코드부터 짜기 시작하죠.

2. "바로 코딩"이 부르는 참사

설계 없이 바로 짜면, 백엔드 프로젝트가 그렇듯 이런 문제가 터집니다.

① 책임이 뒤섞임
   - 주문 조회 코드 안에 RAG 검색이 끼어들고, 답변 생성에 DB 로직이 섞임
   - "이 기능 고치려면 어디를 봐야 하지?"가 안 보임

② 인터페이스가 불명확
   - 함수 이름·입출력이 매번 달라, 나중에 FastAPI로 감쌀 때 고생
   - "이 에이전트를 외부에서 어떻게 부르지?"가 안 정해짐

③ 비용·실패 대비 누락
   - LLM 호출이 몇 번 일어나는지, 실패하면 어쩔지 생각 안 함
   - 운영에서 타임아웃·rate limit 만나면 그대로 멈춤

④ "필요 없는 것"까지 넣음
   - 도구 4개뿐인데 멀티에이전트로 거창하게 → 복잡도·비용만 폭증

특히 ④가 흔합니다. "멋져 보여서" RAG·멀티에이전트를 다 넣었다가 오히려 느리고 비싸고 디버깅 어려운 시스템이 되죠.

3. 에이전트도 "백엔드 서비스"다

핵심 인식 전환입니다.

에이전트 = 입력을 받아 처리해 출력을 내는 하나의 백엔드 서비스.

백엔드 서비스를 설계 없이 만들면 운영에서 터지듯, 에이전트도 똑같습니다. 그래서 설계 → 구현 순서를 지켜야 합니다.

[바로 코딩]   코드부터 → 중간에 구조가 흔들림 → 갈아엎기 → 시간 낭비
[설계 먼저]   무엇을·어떻게 만들지 합의 → 구현은 채우기만 → 흔들림 없음

4. 이번 강이 하는 일 — 코드 대신 "설계 문서"

28강은 코드를 거의 안 짭니다. 대신 설계 문서를 만듭니다. 그리고 그 설계를 코드 스켈레톤(시그니처 + TODO) 으로 박제합니다.

이번 강의 결과물:
  - "승승장구몰 통합 CS 에이전트" 설계 문서
  - ch28_design.py — 함수 시그니처 + TODO 만 있는 '살아있는 설계 문서'
    (실행하면 설계 요약을 출력. 실제 LLM 호출은 30강에서)

30강에서는 이 스켈레톤의 TODO를 채우기만 하면 됩니다. 설계가 미리 고정돼 있어 구현이 흔들리지 않죠.

5. 5단계 설계 절차 (이번 강의 뼈대)

이번 강은 다음 5단계를 따라갑니다.

1단계. 요구사항 정의    — "무엇을 해결하나" (사용자 시나리오)       → 02번
2단계. 기능 분해        — 요구사항을 함수 단위로 쪼갬              → 02번
3단계. 구성요소 필요성 판단 — 도구·RAG·메모리·멀티에이전트 중 뭐가 필요? → 03번 (가장 중요)
4단계. 아키텍처 설계    — 전체 그림(다이어그램)                    → 04번
5단계. 인터페이스 설계  — 외부 계약(진입 함수·엔드포인트)           → 04번

이 절차는 에이전트뿐 아니라 모든 백엔드 설계에 통하는 사고법입니다. 특히 3단계(구성요소 필요성 판단) 가 핵심 — "필요 없는 건 안 넣는다"가 좋은 설계의 출발입니다.

핵심 정리

  • 30강에서 도구·RAG·메모리·멀티에이전트를 하나의 서비스로 통합한다.
  • 설계 없이 바로 코딩하면: 책임 혼재·인터페이스 불명확·비용/실패 누락·과잉 구성.
  • 에이전트도 하나의 백엔드 서비스 — 설계 → 구현 순서를 지켜야 한다.
  • 이번 강은 코드 대신 설계 문서 + 코드 스켈레톤(살아있는 설계 문서)을 만든다.
  • 5단계 절차: 요구사항 → 기능 분해 → 구성요소 판단 → 아키텍처 → 인터페이스.
