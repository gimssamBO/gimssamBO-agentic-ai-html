구성요소 필요성 판단 (3단계 — 가장 중요)

한 줄 요약

설계에서 가장 중요한 단계입니다. 도구·RAG·단기메모리·장기메모리·멀티에이전트 중 무엇이 정말 필요한지를 판단 기준으로 결정합니다. 핵심 원칙은 단 하나 — 필요 없는 구성요소는 넣지 않는다. "멋져 보여서" 넣으면 복잡도·비용만 늘어납니다.

1. "다 넣으면 좋은 거 아냐?" — 아닙니다

흔한 오해입니다. RAG도 좋고 멀티에이전트도 멋지니 다 넣으면 강력하지 않을까?

[다 넣은 시스템]
   도구 + RAG + 장기메모리 + 멀티에이전트 + 워크플로우 + ...
   → LLM 호출 폭증(비용↑) + 지연↑ + 디버깅 지옥 + 유지보수 부담
   → 정작 도구 4개로 충분했던 일을 거창하게 만듦

[필요한 것만 넣은 시스템]
   도구 4개 + RAG + 단기메모리
   → 단순·빠름·저렴·디버깅 쉬움

좋은 설계는 더하는 게 아니라 빼는 것입니다. 각 구성요소는 그만한 값(복잡도·비용) 을 치릅니다. 그 값을 치를 만큼 꼭 필요한지 따져야 하죠.

2. 판단 기준표

각 구성요소를 "이럴 때 필요하다"는 기준으로 판단합니다.

구성요소 "필요하다"고 판단하는 기준 우리 케이스
Tool(도구) 실시간·구조화 데이터 조회/행동이 필요 ✅ 주문/재고/FAQ
RAG 양 많고 자주 바뀌는 문서를 근거로 답해야 함 ✅ 정책/멤버십 PDF
단기 메모리 한 대화 안에서 이전 발화를 참조 ✅ "아까 그거"
장기 메모리 세션을 넘어 사용자별 정보 기억 ❌(이번 범위 밖)
멀티에이전트 도구 5~7개 초과 또는 책임 충돌 △(도구 4개 → 단일로 시작)

각 결정을 하나씩 봅시다.

3. 도구(Tool) — ✅ 필요

기준: 실시간·구조화 데이터 조회나 행동이 필요한가?

주문 상태(R2)·재고(R3)·FAQ(R4)는 모두 DB/CSV에 있는 실시간·구조화 데이터입니다. LLM이 지어낼 수 없고 조회해야 하죠. → 도구 필요. (1강에서 "LLM이 답 못 한" 바로 그 이유)

4. RAG — ✅ 필요

기준: 양 많고 자주 바뀌는 문서를 근거로 답해야 하는가?

환불·멤버십 정책(R1)은 PDF 문서에 길게 적혀 있고, 회사 사정에 따라 바뀝니다. 이걸 프롬프트에 다 욱여넣을 수 없고, 지어내서도 안 됩니다. → 문서를 검색해 근거로 답하는 RAG 필요.

RAG가 맞는 경우:   긴 문서·자주 바뀜·근거(출처) 필요 → 정책 PDF
RAG가 과한 경우:   답이 고정적이고 짧음 → 그냥 프롬프트에 넣으면 됨
실시간 데이터:     RAG 아님! → 도구로 조회 (주문·재고는 문서가 아니라 DB)

주의 — "실시간 데이터(주문·재고)"는 RAG가 아니라 도구입니다. RAG는 고정된 문서를 검색하는 것이지, 시시각각 변하는 DB 값을 가져오는 게 아닙니다. 이 구분이 자주 헷갈립니다.

5. 단기 메모리 — ✅ 필요 / 장기 메모리 — ❌ 이번엔 불필요

단기 기준: 한 대화 안에서 이전 발화를 참조하는가?
장기 기준: 세션을 넘어 사용자별 정보를 기억해야 하는가?

"아까 그 정책 다시"(R5)는 같은 대화 안의 맥락 참조라 → 단기 메모리(thread_id, 19강)면 충분합니다.

반면 "이 사용자가 한 달 전에 뭘 샀는지" 같은 세션을 넘는 기억은 이번 범위가 아닙니다. → 장기 메모리는 불필요. (필요해지면 20강 SQLite 방식으로 나중에 추가)

단기 메모리: 한 대화 세션 = thread_id 별 → ✅ (R5)
장기 메모리: 세션 넘는 사용자 프로필    → ❌ (이번엔 범위 밖, 과잉)

6. 멀티에이전트 — △ 단일로 시작

기준: 도구 5~7개 초과이거나 책임이 충돌하는가?

우리는 도구가 4개뿐입니다. 단일 create_agent 하나가 충분히 다룰 수 있죠. 굳이 역할을 나눠 멀티에이전트로 만들면 복잡도·비용만 늘어납니다.

멀티에이전트가 맞는 때:  도구 8개+ / 역할이 뚜렷이 갈림(리서처·분석가·작성자)
우리 케이스:           도구 4개, 단일 책임 → 단일 에이전트로 시작
                      (나중에 도구가 늘면 그때 분리해도 늦지 않음)

설계 원칙 재확인: 멀티에이전트는 도구가 적으면 오히려 손해입니다. 단일로 시작하고, 정말 복잡해지면 그때 나눈다. "나중에 나누기"는 쉽지만, 처음부터 과하게 나누면 되돌리기 어렵습니다.

7. 판단 결과 — 설계 확정

3단계를 거친 결론:

✅ 도구 4개  : get_order_status, get_stock, search_faq, policy_search
✅ RAG       : 정책/멤버십 PDF 검색 (policy_search 내부)
✅ 단기메모리 : thread_id 별 대화 세션
❌ 장기메모리 : 이번 범위 밖
❌ 멀티에이전트: 단일 create_agent 로 시작 (도구 4개)

"무턱대고 다 넣기" 대신 기준으로 따져 넣을 것과 뺄 것을 정했습니다. 이 의사결정 과정 자체가 설계의 핵심이고, 06번에서는 이 판단을 규칙으로 자동화한 도우미를 만들어 봅니다.

핵심 정리

  • 3단계는 가장 중요 — 도구·RAG·메모리·멀티에이전트 중 무엇이 필요한지 기준으로 판단.
  • 핵심 원칙: 필요 없는 건 넣지 않는다(각 구성요소는 복잡도·비용을 치름).
  • 도구=실시간·구조화 데이터, RAG=긴/변하는 문서 근거, 단기메모리=한 대화 맥락.
  • 실시간 데이터는 RAG가 아니라 도구 (자주 헷갈리는 구분).
  • 멀티에이전트는 도구 5~7개 초과/책임 충돌 시 — 우리는 4개라 단일로 시작.
  • 다음 절에서 4·5단계 — 아키텍처와 인터페이스를 설계합니다.
