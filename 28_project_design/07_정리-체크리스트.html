정리 & 체크리스트

이번 강에서 배운 것

28강은 코드를 거의 안 짜고 설계 사고법을 배웠습니다. 흩어진 기술들을 하나의 서비스로 묶기 전에, 무엇을·어떻게 만들지 먼저 정하는 단계입니다.

  • 바로 코딩의 위험 (01번) — 설계 없이 짜면 책임 혼재·인터페이스 불명확·비용/실패 누락·과잉 구성. 에이전트도 백엔드 서비스 — 설계 → 구현 순서를 지킨다.
  • 요구사항·기능 분해 (02번) — "무엇을 해결하나"를 사용자 시나리오(R1~R5) 로 적고, 각각을 함수(입력→출력) 로 쪼갠다.
  • 구성요소 판단 (03번, 가장 중요) — 도구·RAG·메모리·멀티에이전트 중 필요한 것만 기준으로 선별. 필요 없는 건 넣지 않는다.
  • 아키텍처·인터페이스 (04번) — 전체 그림을 그리고, 단일 진입점 answer(message, thread_id) 로 외부 계약을 정한다.
  • 코드 스켈레톤 (05번) — 설계를 시그니처 + TODO로 박제한 살아있는 설계 문서(ch28_design.py).
  • 트레이드오프 자동화 (06번) — 구성요소 판단을 규칙 도우미로 만들어 다른 프로젝트에도 일관 적용.

5단계 설계 절차 한눈에

1. 요구사항 정의    "무엇을 해결하나" → 사용자 시나리오 (R1~R5)
2. 기능 분해        요구사항 → 함수(입력→출력)
3. 구성요소 판단    도구·RAG·메모리·멀티에이전트 중 필요한 것만  ← 가장 중요
4. 아키텍처         전체 그림(데이터 흐름 다이어그램)
5. 인터페이스       외부 계약 (answer 진입점·thread_id·엔드포인트·실패·비용)

구성요소 판단 기준 (핵심 표)

구성요소 "필요하다"는 기준 통합 CS 에이전트
도구 실시간·구조화 데이터 조회/행동 ✅ 주문·재고·FAQ
RAG 양 많고 자주 바뀌는 문서 근거 ✅ 정책 PDF
단기 메모리 한 대화 안 맥락 참조 ✅ "아까 그거"
장기 메모리 세션 넘는 사용자별 기억 ❌ 범위 밖
멀티에이전트 도구 5~7개 초과 / 책임 충돌 ❌ 도구 4개 → 단일

기억할 한 가지: 실시간 데이터(주문·재고)는 RAG가 아니라 도구다.

설치 라이브러리

conda activate agentic
pip install pyyaml          # 30강 config 로드 대비 (이번 강은 표준 dataclass만으로도 충분)
  • 이번 강은 LLM 호출이 없습니다. dataclass로 설계를 박제하고 실행하면 요약을 출력.
  • ch28_design.py는 30강 구현의 스켈레톤 — TODO를 30강에서 채웁니다.

체크리스트

  • [ ] 설계 없이 바로 코딩하면 생기는 문제 4가지를 말할 수 있다.
  • [ ] 5단계 설계 절차를 순서대로 말할 수 있다.
  • [ ] 도구/RAG/단기·장기메모리/멀티에이전트의 필요성 판단 기준을 안다.
  • [ ] 실시간 데이터는 RAG가 아니라 도구임을 안다.
  • [ ] 단일 진입점 answer(message, thread_id)로 인터페이스를 설계할 수 있다.
  • [ ] 비용·지연·실패 대비를 설계 단계에서 고려해야 함을 안다.

한 줄 핵심

"설계 → 구현. 그리고 필요 없는 건 넣지 않는다." — 좋은 설계는 기능을 더하는 게 아니라, 꼭 필요한 것만 남기는 것이다.

다음 강 예고 — 29강

설계를 마쳤으니, 이제 그 에이전트를 실제로 운영할 차례입니다. 29강은 "내 PC에선 됐는데요" 문제를 다룹니다 — 설정 분리(.env/config), 구조적 로깅, 예외 처리·재시도(지수 백오프), 비용·지연 관리, FastAPI로 감싸기, 응답 캐싱. 28강에서 "설계로 미리 챙긴" 운영 고려사항들을 실제 코드로 구현합니다. 그리고 30강에서 드디어 이 모든 설계를 완성형 에이전트로 구현합니다.
