Planner / Worker 협업 구조

한 줄 요약

Planner는 전략가(무엇을 할지), Worker는 실무자(어떻게 할지)입니다. Planner가 작업을 JSON 리스트로 쪼개면 Worker가 한 작업씩 충실히 수행하고, 마지막에 산출물을 취합합니다. 에이전트 간 데이터는 구조화 출력(JSON) 으로 안전하게 주고받습니다.

1. 세 단계 구조

캠페인 1건 이 세 단계를 거칩니다.

  1. [Planner] 전략가 — 실행은 안 하고 '무엇을 할지' 결정 → ["타깃 분석", "카피 작성", "예산 배분"] (구조화 출력 JSON)
  2. [Worker] 실무자 — 받은 '한 작업만' 충실히 수행(반복): 작업1 → 산출물1, 작업2 → 산출물2, 작업3 → 산출물3
  3. [취합] Worker 산출물을 모아 최종 실행안으로 정리
역할 하는 일 특징
Planner 무엇을 할지 결정 → 하위 작업 리스트 실행 안 함, 계획만
Worker 받은 한 작업만 수행 재사용·병렬화 가능
취합 산출물을 모아 정리 최종 결과 생성

2. Planner — 전략가

Planner는 실행하지 않습니다. 오직 "무엇을 할지"만 정하죠.

PLANNER_SYSTEM = (
    "너는 마케팅 캠페인 '기획 설계자(Planner)'다. "
    "주어진 캠페인 브리프를 보고, 실행에 필요한 하위 작업을 3~4개로 쪼개라. "
    "작업은 서로 겹치지 않게, 한 문장 명령형으로 작성하라. 실행은 하지 마라."  # ← 실행 금지!
)

프롬프트의 "실행은 하지 마라" 가 핵심입니다. Planner가 욕심내서 직접 카피까지 쓰면 안 됩니다 — 쪼개기만 하고 실행은 Worker에게 넘겨야 역할 분리가 유지되죠. 또 "서로 겹치지 않게" 로 작업 중복을 막고, "한 문장 명령형" 으로 Worker가 받기 좋은 형태를 강제합니다.

3. Worker — 실무자

Worker는 받은 한 작업만 깊이 수행합니다.

WORKER_SYSTEM = (
    "너는 마케팅 '실무 작업자(Worker)'다. "
    "주어진 캠페인 브리프 맥락에서, 지정된 '하나의 작업'만 구체적으로 수행하라. "  # ← 한 작업만!
    "결과는 5줄 이내로 실무에 바로 쓸 수 있게 작성하라."
)

"지정된 하나의 작업만" 이 핵심입니다. Worker는 전체 캠페인을 보지 않고, 자기에게 주어진 작업 하나에만 집중하죠. 그래서:

- 같은 Worker 함수를 작업마다 재사용 (work(brief, 작업1), work(brief, 작업2)...)
- 작업이 독립적이라 병렬 실행 가능
- 한 작업 실패해도 그것만 재시도 (07번)

Worker는 캠페인 브리프(맥락)와 자기 작업 하나를 받아 결과를 냅니다. 맥락을 주는 건 "전체 그림 안에서 이 작업을 하라"는 뜻이죠.

4. 에이전트 간 데이터는 "구조화"로

가장 중요한 설계 포인트입니다. Planner가 작업을 자연어 문단으로 주면 Worker에게 넘길 때 깨집니다.

[나쁜 예 — 자유 텍스트]
Planner: "먼저 타깃을 분석하고, 그 다음 카피를 쓰고, 예산도 배분하세요."
   → 코드가 이 문장을 어떻게 작업 리스트로 쪼개지? (파싱 지옥)

[좋은 예 — 구조화 출력]
Planner: ["타깃 분석", "카피 작성", "예산 배분"]   (JSON list)
   → for task in subtasks: work(task)  (바로 반복 가능!)

그래서 Planner 출력을 JSON 리스트로 강제합니다(8강 with_structured_output).

from pydantic import BaseModel, Field

class Plan(BaseModel):
    """Planner가 만드는 실행 계획(구조화 출력 스키마)."""
    subtasks: list[str] = Field(description="이 캠페인을 위해 필요한 하위 작업 3~4개")

list[str]로 강제하면, LLM이 무슨 말을 하든 결과가 리스트로 보장됩니다. 코드는 for task in plan.subtasks로 바로 돌리죠. 파싱 실수가 사라집니다.

이건 백엔드에서 서비스 간 통신에 JSON 스키마(DTO) 를 쓰는 것과 똑같은 원칙입니다 — "자유 텍스트 말고 정해진 형식으로 주고받자."

5. 온도(temperature) 분리

Planner와 Worker는 다른 temperature를 씁니다.

llm_plan = get_chat(temperature=0)      # 계획은 일관성·재현성이 중요 → 0
llm_work = get_chat(temperature=0.5)    # 카피 등 창의 작업은 다양성이 도움 → 0.5

Planner (temperature=0):
   계획은 매번 비슷해야 함 (재현성) → 무작위성 제거
Worker (temperature=0.5):
   카피·아이디어는 창의성·다양성이 필요 → 약간 높임

같은 LLM이라도 역할에 맞게 온도를 조절합니다. 분류·계획은 0, 창작은 0.5~0.7 — 이 감각이 중요하죠(2강 temperature).

6. 취합 — 산출물 모으기

Worker들의 산출물을 모아 하나의 문서로 정리합니다.

report = [f"# 캠페인 실행안\n\n> {brief_text}\n"]
for i, (task, output) in enumerate(outputs, 1):
    report.append(f"## {i}. {task}\n{output}\n")
final = "\n".join(report)

각 작업을 ## 1. 타깃 분석, ## 2. 카피 작성처럼 섹션으로 묶어 읽기 좋은 실행안을 만듭니다. Planner가 쪼갠 작업이 그대로 문서의 목차가 되는 셈이죠.

핵심 정리

  • Planner(전략가): 실행 안 하고 작업을 JSON 리스트로 분해("실행 금지" 명시).
  • Worker(실무자): 받은 한 작업만 깊이 수행(재사용·병렬·재시도 유리).
  • 에이전트 간 데이터는 구조화 출력(list[str])으로 → 파싱 실수 제거(DTO 원칙).
  • 온도 분리: Planner는 0(재현성), Worker는 0.5(창의성).
  • 취합: Worker 산출물을 섹션으로 묶어 최종 실행안.
