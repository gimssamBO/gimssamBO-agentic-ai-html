정리 & 체크리스트

이번 강에서 배운 것

26강은 "무엇을 할지(계획)"와 "어떻게 할지(실행)"를 다른 역할로 나누는 Planner/Worker 구조를 다뤘습니다.

  • 왜 나누나 (01·02번) — 한 LLM에게 "계획도 세우고 실행도 하라"고 하면 둘 다 어설퍼집니다. Planner가 작업을 쪼개고 Worker가 한 작업씩 집중 수행하면, 각자 잘하는 일에만 몰두해 품질이 올라갑니다.
  • Supervisor와의 차이 (03번) — 25강 Supervisor는 "이 질문을 누구에게 보낼까"라는 라우팅이고, Planner/Worker는 "이 목표를 어떤 작업들로 쪼갤까"라는 분해입니다. 라우팅은 하나를 고르고, 분해는 여러 작업을 만들어 모읍니다.
  • Planner (04번) — with_structured_output(Plan)으로 작업을 항상 리스트(list[str])로 받아, 코드가 바로 for로 순회할 수 있게 합니다.
  • Worker (05번) — 받은 한 작업만 맥락(브리프)과 함께 수행합니다. 작업이 독립적이라 재사용·병렬화·재시도에 유리합니다.
  • 오케스트레이터 (06번) — run_campaign이 계획 → 실행 → 취합을 지휘합니다. Planner가 쪼갠 작업이 그대로 최종 문서의 목차가 됩니다.
  • 실패 처리 (07번) — Worker 한 번 실패에 전체가 멈추지 않도록, 재시도 → 스킵·기록 → 끝까지 진행(부분 실패 허용)을 더했습니다.

핵심 코드 한눈에

# 1) Planner — 목표를 작업 리스트로 분해 (구조화 출력)
class Plan(BaseModel):
    subtasks: list[str] = Field(description="필요한 하위 작업 3~4개")

def plan(llm, brief_text: str) -> list[str]:
    planner = llm.with_structured_output(Plan)
    result = planner.invoke([SystemMessage(PLANNER_SYSTEM),
                             HumanMessage(f"[캠페인 브리프]\n{brief_text}")])
    return result.subtasks

# 2) Worker — 한 작업만 맥락과 함께 수행
def work(llm, brief_text: str, subtask: str) -> str:
    result = llm.invoke([SystemMessage(WORKER_SYSTEM),
                         HumanMessage(f"[브리프]\n{brief_text}\n\n[작업]\n{subtask}")])
    return result.content

# 3) 오케스트레이터 — 계획→실행→취합
def run_campaign(brief_text: str) -> str:
    llm_plan = get_chat(temperature=0)      # 계획은 재현성
    llm_work = get_chat(temperature=0.5)    # 실행은 약간의 다양성
    subtasks = plan(llm_plan, brief_text)
    outputs = [(t, work(llm_work, brief_text, t)) for t in subtasks]
    report = [f"# 캠페인 실행안\n\n> {brief_text}\n"]
    for i, (t, out) in enumerate(outputs, 1):
        report.append(f"## {i}. {t}\n{out}\n")
    return "\n".join(report)

체크리스트

  • [ ] Planner와 Worker로 역할을 나누면 왜 품질이 오르는지 설명할 수 있다.
  • [ ] Supervisor(라우팅)와 Planner/Worker(분해)의 차이를 한 문장으로 말할 수 있다.
  • [ ] with_structured_output(Plan)이 왜 자유 텍스트보다 안전한지 안다(항상 리스트).
  • [ ] Worker에 작업만이 아니라 맥락(브리프)도 함께 주는 이유를 안다.
  • [ ] 오케스트레이터의 세 책임(순서 제어·데이터 전달·취합)을 설명할 수 있다.
  • [ ] Worker 실패 시 재시도 → 스킵·기록 → 계속(부분 실패 허용)을 구현할 수 있다.

한 줄 핵심

"계획(Planner)과 실행(Worker)을 나누고, 오케스트레이터가 지휘한다." — 한 명에게 다 시키지 말고, 쪼개서 각자 잘하는 일에 집중시켜라.

다음 강 예고 — 27강

26강의 오케스트레이터는 for 루프로 흐름을 제어했습니다. 27강에서는 이 지휘를 StateGraph(그래프) 로 옮깁니다. Researcher → Analyst → Writer가 공유 상태를 주고받는 파이프라인을 그래프로 선언하고, 조건부 분기로 품질을 재검토하는 데까지 나아갑니다. 즉, "코드로 흐름을 짜던 것"을 "그래프로 흐름을 선언하는 것" 으로 바꾸는 단계입니다.
