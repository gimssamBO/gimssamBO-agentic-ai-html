만능 한 명 vs 전문가 팀

한 줄 요약

24강까지는 도구를 여러 개 단 하나의 에이전트를 만들었습니다. 기능이 쌓이면 프롬프트가 수백 줄이 되고 도구가 10개를 넘어 LLM이 헷갈리죠. 해결책은 역할별 전문 에이전트로 쪼개고, 앞단에 라우터(Supervisor)를 두는 멀티에이전트입니다.

1. 만능 한 명의 한계

승승장구몰 CS 에이전트에 기능이 하나씩 쌓이는 상황을 상상해 봅시다.

처음:  주문 조회만 → 잘 됨
한 달 뒤: 주문 조회 + 환불 정책 + 상품 추천 + 쿠폰 + 재고 + 배송조회...
   → 시스템 프롬프트가 "주문은 이렇게, 환불은 저렇게, 추천은 또..." 수백 줄
   → 도구가 get_order, get_stock, recommend, policy_search, refund, coupon... 10개+
   → LLM이 "어느 도구를 써야 하지?" 자주 헷갈림
   → 한 군데 고치면 다른 기능이 깨짐

한 명에게 모든 일을 시키니, 만능이 아니라 어중간해지는 거죠.

2. 백엔드 개발자에게 익숙한 문제

이건 사실 백엔드 개발자가 잘 아는 문제입니다.

[하나의 거대한 God Object 서비스]
   모든 기능이 한 클래스/서비스에 → 비대·결합·수정 위험
        ↓ 해결책
[마이크로서비스 + API Gateway]
   책임별로 서비스를 쪼개고, 앞단 라우터가 알맞은 곳으로 보냄

에이전트 세계의 해결책도 똑같습니다. 역할(책임)별로 에이전트를 쪼개고, 앞단에 라우터를 둡니다. 이게 멀티에이전트(Multi-Agent) 입니다.

3. 전문가 팀으로 나누기

승승장구몰 CS를 전문가 팀으로 재구성하면:

  • [만능 한 명] 하나의 에이전트 — 프롬프트 수백 줄 / 도구 10개+ / 도구 선택 혼동
  • [전문가 팀] Supervisor(라우터) 가 질문을 알맞은 전문가에게 보냄:
  • 추천 전문 에이전트 (상품 도구만)
  • 정책 전문 에이전트 (FAQ 도구만)
  • 주문 전문 에이전트 (조회 도구만)

각 전문가는:

- 짧은 프롬프트 (자기 역할만)
- 적은 도구 (자기 책임만) → 도구 선택 정확
- 독립적 (한 명 고쳐도 다른 명 안 깨짐)

회사에서도 "한 명이 모든 부서 일"보다 "부서별 전문가 + 안내데스크"가 효율적이듯, 에이전트도 마찬가지죠.

4. 멀티에이전트의 진짜 의미

흔한 오해부터 바로잡습니다.

[오해]  멀티에이전트 = AI를 여러 개 띄우는 것
[진짜]  멀티에이전트 = 역할(책임)별로 프롬프트와 도구 집합을 분리하고,
                      그 사이의 흐름(라우팅/인계)을 코드로 설계하는 일

핵심은 "AI 개수"가 아니라 "책임 분리 + 흐름 설계" 입니다. 같은 LLM을 쓰더라도, 프롬프트와 도구를 역할별로 나누고 라우터로 연결하면 멀티에이전트죠. 24강까지의 "단일 에이전트 + 여러 도구"를, "여러 전문 에이전트 + 라우터"로 재구성하는 겁니다.

5. 우리가 만들 것

이번 강에서는 두 전문 에이전트 + Supervisor를 만듭니다.

고객 질문 → [Supervisor 라우터] "이건 추천? 정책?"

  • 추천 질문 → [추천 에이전트] (products.csv 도구)
  • 정책 질문 → [정책 에이전트] (faq.csv 도구)

→ 알맞은 전문가의 답변

  • 추천 에이전트(sales): products.csv로 상품 추천.
  • 정책 에이전트(policy): faq.csv로 환불·배송 등 정책 안내.
  • Supervisor: 질문을 보고 둘 중 하나에게 위임.

그리고 라우터를 규칙(키워드) vs LLM(의미 이해) 두 방식으로 만들어 비교합니다(06번 신규).

6. 언제 쪼개야 하나

"무조건 쪼개라"는 아닙니다. 분리 시점의 기준:

- 도구가 5~7개를 넘는다
- 책임이 명확히 갈린다 (추천 vs 정책 vs 주문)
- 프롬프트가 너무 길어 LLM이 혼동한다
- 한 기능 수정이 다른 기능을 깨뜨린다

반대로 도구 2~3개의 작은 에이전트는 굳이 쪼갤 필요 없습니다. 쪼개면 라우팅 복잡도가 늘어나니까요. "God Object가 됐을 때 쪼갠다" — 이 판단력이 중요합니다(28강 설계에서 더 다룸).

핵심 정리

  • 만능 한 에이전트는 기능이 쌓이면 프롬프트 비대·도구 과다·수정 위험.
  • 이건 백엔드의 God Object 문제 → 해결책은 마이크로서비스 + 라우터.
  • 멀티에이전트 = 역할별 프롬프트·도구 분리 + 흐름(라우팅) 설계(AI 개수 아님).
  • 각 전문 에이전트는 짧은 프롬프트·적은 도구로 정확·독립적.
  • 이번 강: 추천/정책 에이전트 2개 + Supervisor 라우터.
  • 쪼개는 시점: 도구 5~7개 초과·책임 분리·혼동·수정 위험.
