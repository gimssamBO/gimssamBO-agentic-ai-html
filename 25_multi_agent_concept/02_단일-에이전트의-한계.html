단일 에이전트의 한계

한 줄 요약

단일(거대) 에이전트와 멀티에이전트를 항목별로 비교하면 차이가 분명합니다. 도구가 5~7개를 넘고 책임이 명확히 갈린다면, 역할별로 쪼개 도구 선택 정확도·유지보수·비용을 모두 개선할 시점입니다.

1. 항목별 비교

항목 단일(거대) 에이전트 멀티에이전트
시스템 프롬프트 모든 규칙을 한 곳에(수백 줄) 역할별로 짧게 분리
도구 수 전부 한 에이전트에(과다) 역할에 필요한 것만
도구 선택 정확도 낮음(혼동) 높음(후보가 적음)
유지보수 수정 시 부작용 큼 역할 단위로 격리
테스트 통합 테스트만 에이전트별 단위 테스트
비용/지연 긴 프롬프트로 토큰↑ 짧은 프롬프트로 절약

하나씩 자세히 봅시다.

2. 도구 선택 정확도 — 핵심 문제

가장 중요한 차이입니다. 6강에서 배웠듯, LLM은 도구 설명(docstring)을 읽고 어느 도구를 쓸지 판단합니다. 도구가 많아지면 이 판단이 흔들리죠.

[도구 10개인 단일 에이전트]
   "환불 문의" → get_order? refund? policy_search? coupon?
   → 비슷한 도구들 사이에서 LLM이 헷갈림 → 엉뚱한 도구 호출

[도구 1개인 정책 전문 에이전트]
   "환불 문의" → search_faq (선택지가 하나라 헷갈릴 수 없음)
   → 정확

후보가 적으면 선택이 정확합니다. 사람도 "10개 메뉴 중 고르기"보다 "2개 중 고르기"가 쉽듯, LLM도 도구가 적을수록 정확하죠. 역할 분리의 가장 직접적인 효과입니다.

3. 프롬프트 비대화

단일 에이전트는 모든 규칙을 한 프롬프트에 욱여넣습니다.

# 단일 에이전트의 프롬프트 (계속 길어짐)
system_prompt = """
너는 승승장구몰 상담원이다.
- 주문 조회는 주문번호를 받아 get_order로...
- 환불은 7일 이내만 가능하고 절차는...
- 상품 추천은 카테고리를 받아...
- 쿠폰은 등급별로 다르고...
- 배송 조회는...
(수백 줄 계속)
"""

# 멀티에이전트 — 각자 짧게
sales_prompt = "너는 '상품 추천' 전문 상담원이다. 추천 외 질문은 정책 담당에 안내하라."
policy_prompt = "너는 '정책/FAQ 안내' 전문 상담원이다. FAQ 근거로만 답하라."

프롬프트가 짧아지면:

- LLM이 자기 역할에 집중 (잡음 적음)
- 토큰이 줄어 비용·지연 감소 (매 호출마다 긴 프롬프트를 안 보냄)
- 사람이 읽고 수정하기 쉬움

4. 유지보수 — 격리의 가치

단일 에이전트는 한 곳을 고치면 다른 곳이 깨질 위험이 있습니다.

[단일] "환불 정책 문구 수정" → 같은 프롬프트의 추천 로직에 영향?
   → 전체를 다시 테스트해야 안심

[멀티] "환불 정책 수정" → policy_agent만 수정·테스트
   → sales_agent는 건드리지 않았으니 안전

역할별로 격리돼 있어, 수정 범위가 명확합니다. 백엔드의 마이크로서비스가 "한 서비스 배포가 다른 서비스에 영향 없게" 하는 것과 같죠.

5. 테스트 — 단위 테스트 가능

[단일] 통합 테스트만 가능 — "전체 시나리오를 돌려봐야" 검증
[멀티] 에이전트별 단위 테스트 — "추천 에이전트만" 따로 검증 가능

# 멀티에이전트는 각 에이전트를 독립적으로 테스트
def test_sales_agent():
    r = sales_agent.invoke({"messages": [{"role": "user", "content": "전자기기 추천"}]})
    assert "원" in r["messages"][-1].content   # 상품 추천이 나왔는지

def test_policy_agent():
    r = policy_agent.invoke({"messages": [{"role": "user", "content": "환불 기간"}]})
    assert "7일" in r["messages"][-1].content   # 정책 답변이 나왔는지

작은 단위로 테스트하니 어디가 문제인지 빨리 찾습니다.

6. 분리의 비용 — 공짜가 아니다

물론 멀티에이전트도 단점이 있습니다.

- 라우팅 로직이 추가됨 (Supervisor를 만들고 관리)
- 라우터가 틀리면 엉뚱한 에이전트로 감 (오라우팅)
- 에이전트 간 흐름 추적이 복잡해질 수 있음
- 너무 잘게 쪼개면 오히려 관리 부담

그래서 "무조건 쪼개라"가 아니라 "God Object가 됐을 때 쪼개라" 입니다. 도구 2~3개의 작은 에이전트는 단일로 두는 게 낫죠. 트레이드오프를 보고 판단하는 게 핵심입니다(28강 설계).

핵심 정리

  • 단일 vs 멀티: 프롬프트·도구·정확도·유지보수·테스트·비용 전반에서 차이.
  • 핵심 효과: 도구 후보가 적어 도구 선택 정확도 ↑(6강 docstring 매칭).
  • 프롬프트가 짧아져 집중·비용·가독성 개선.
  • 역할별 격리로 수정 범위 명확, 단위 테스트 가능.
  • 단, 라우팅 복잡도·오라우팅 위험이라는 비용도 존재.
  • 판단 기준: 도구 5~7개 초과·책임 분리·혼동 → 그때 쪼갠다.
