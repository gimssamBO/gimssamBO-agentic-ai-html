도구가 많아지면 생기는 문제 — "도구 상자가 커지면 헷갈린다"

한 줄 요약

5강에서는 도구가 2개뿐이었습니다. 하지만 진짜 에이전트는 수많은 도구를 갖습니다. 도구가 많아지면 "어떤 도구를 써야 하지?" 라는 새 문제가 생깁니다. 좋은 소식은, 하드코딩 없이 도구 설명(독스트링)만 잘 쓰면 모델이 알아서 고른다는 것입니다.

1. 도구가 늘어나면 생기는 일

5강의 에이전트는 도구가 get_stock, get_exchange_rate 둘뿐이었습니다. 질문이 오면 둘 중 하나를 고르면 됐죠. 하지만 진짜 승승장구몰 CS 에이전트는 이런 도구를 다 가집니다.

  • 재고 조회, 가격 조회, 주문 상태 확인, 상품 검색, 환불 정책 안내, 리뷰 요약, 배송 추적…

도구가 10개, 20개로 늘면 새 문제가 생깁니다.

# "이 청바지 얼마예요?" 라는 질문에...
# 모델이 get_order_status(주문 조회)를 부르면? → 엉뚱한 답!
# 모델이 get_price(가격 조회)를 부르면? → 정답!

여러 도구 중 옳은 하나(또는 여럿)를 정확히 고르는 능력이 에이전트 품질을 좌우합니다.

비유: 공구함에 망치 하나만 있으면 고민이 없습니다. 하지만 드라이버·렌치·펜치가 수십 개면, "이 일엔 어떤 공구?" 를 고르는 게 일이 됩니다. 잘못 고르면 나사를 망치로 두드리는 꼴이죠.

2. 하드코딩은 답이 아니다

"그럼 우리가 직접 정해 주면 되잖아?"라고 생각할 수 있습니다.

# 나쁜 방법 — if문으로 일일이 하드코딩
if "얼마" in question:
    get_price(...)
elif "재고" in question:
    get_stock(...)
elif "주문" in question:
    get_order_status(...)
# ... 도구가 20개면 if문이 20개? 그리고 "값이 어때?"는 "얼마"에 안 걸림!

이 방식은 도구가 늘 때마다 if문이 늘고, 표현이 조금만 달라도("얼마" vs "값이 어때?" vs "가격은?") 놓칩니다. 유지보수 지옥입니다.

3. 진짜 해법 — 설명을 잘 쓰면 모델이 고른다

좋은 소식이 있습니다. 우리가 도구 선택을 하드코딩할 필요가 전혀 없습니다. 도구의 독스트링(설명) 을 잘 써 두면, 모델이 질문과 설명을 비교해 알아서 고릅니다.

def get_price(product_name: str) -> str:
    """상품명을 받아 판매가(원)를 반환한다. 가격/얼마 질문에 사용."""  # <- 이게 독스트링
    ...

# 4개 도구를 그냥 다 등록만 하면...
TOOLS = [get_price, get_stock, get_order_status, search_product]

ask("슬림핏 청바지 얼마야?")    # → 모델이 get_price 를 알아서 고름!
ask("이어버드 재고 있어?")      # → 모델이 get_stock 을 알아서 고름!

우리는 도구를 그냥 다 등록했을 뿐인데, 질문마다 다른 도구가 선택됩니다. 비결은 독스트링입니다.

4. 이 강의 핵심 메시지

이 강에서 계속 반복할 한 문장이 있습니다.

"도구 설명은 모델을 위한 프롬프트다."

독스트링은 동료 개발자를 위한 메모가 아니라, 모델이 읽고 판단하는 사용 설명서입니다. 그래서 이 강은 결국 "모델이 잘 고를 수 있는 설명을 어떻게 쓰는가"에 관한 강의입니다.

핵심 정리

  • 도구가 많아지면 "올바른 도구 고르기" 가 새 과제가 된다.
  • if문 하드코딩은 유지보수 지옥 → 답이 아니다.
  • 독스트링을 잘 쓰면 모델이 알아서 도구를 고른다.
  • 핵심 한 줄: "도구 설명은 모델을 위한 프롬프트다."
  • 다음 절에서 모델이 무엇을 보고 도구를 고르는지 자세히 봅니다.
