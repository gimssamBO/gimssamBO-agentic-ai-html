계획이 잘못됐을 때 대응 (검증 → 재계획)

한 줄 요약

make_plan이 만든 계획이 항상 좋은 건 아닙니다. 단계가 비었거나 1개뿐이면 분해 실패, 너무 많으면(>8) 과분해입니다. 검증(validate) 으로 적합성을 판정하고, 부적합하면 무엇이 문제인지 피드백을 붙여 재계획(replan) 을 요청합니다.

적용 코드 code/ch08_plan_validate.py

# 실행: python code/ch08_plan_validate.py
from typing import List
from pydantic import BaseModel
from common import get_chat

# 1. LLM 모델 초기화 (OpenAI 사용)
llm = get_chat(provider="openai")

# 2. 계획의 적합 범위 (하위 작업 개수 기준)
MIN_STEPS, MAX_STEPS = 2, 8

# 3. 계획의 구조를 정의하는 스키마
class Plan(BaseModel):
    goal: str
    steps: List[str]

def make_plan(goal: str) -> Plan:
    """목표를 받아 실행 순서대로 하위 작업 목록으로 분해한 계획을 만든다."""
    planner = llm.with_structured_output(Plan)
    prompt = (
        "너는 승승장구몰의 프로젝트 매니저다. 아래 목표를 실행 순서대로 "
        f"{MIN_STEPS}~{MAX_STEPS}개의 구체적 하위 작업으로 분해하라.\n"
        f"목표: {goal}"
    )
    return planner.invoke(prompt)

def validate_plan(plan: Plan):
    """계획의 적합성을 판정한다. (적합여부 bool, 사유 str)를 돌려준다."""
    n = len(plan.steps)
    if n < MIN_STEPS:
        return False, f"단계가 {n}개뿐입니다 — 목표 분해가 부족합니다(최소 {MIN_STEPS}개)."
    if n > MAX_STEPS:
        return False, f"단계가 {n}개로 너무 많습니다 — 과분해입니다(최대 {MAX_STEPS}개)."
    if any(not s.strip() for s in plan.steps):
        return False, "빈 단계가 포함되어 있습니다 — 실행 불가능한 단계입니다."
    return True, "적합한 계획입니다."

def replan(goal: str, reason: str) -> Plan:
    """검증 실패 이유(reason)를 피드백으로 붙여 계획을 다시 세운다."""
    planner = llm.with_structured_output(Plan)
    prompt = (
        "너는 승승장구몰의 프로젝트 매니저다. 이전 계획이 다음 이유로 부적합 판정을 받았다.\n"
        f"부적합 사유: {reason}\n"
        f"이 점을 반드시 고쳐, 목표를 실행 순서대로 {MIN_STEPS}~{MAX_STEPS}개의 "
        f"구체적 하위 작업으로 다시 분해하라.\n목표: {goal}"
    )
    return planner.invoke(prompt)

def plan_with_validation(goal: str, max_replan: int = 2) -> Plan:
    """계획 → 검증 → (부적합 시) 재계획을 최대 max_replan회 반복한다."""
    plan = make_plan(goal)
    for attempt in range(1, max_replan + 1):
        ok, reason = validate_plan(plan)
        print(f"[STEP {attempt}] 검증: {'적합' if ok else '부적합'} — {reason}")
        if ok:
            return plan                       # 통과 → 채택
        print(f"        → 재계획 요청(피드백: {reason})")
        plan = replan(goal, reason)           # 부적합 → 다시 짜기
    return plan

if __name__ == "__main__":
    goal = "승승장구몰 신상품 '가을 패딩' 출시"

    # --- 데모 1: 일부러 단계가 1개뿐인 나쁜 계획을 만들어 검증기가 잡는지 확인 ---
    bad_plan = Plan(goal=goal, steps=["그냥 출시한다"])
    ok, reason = validate_plan(bad_plan)
    print(f"검증: {'적합' if ok else '부적합'} — {reason}")
    # → 부적합 — 단계가 1개뿐입니다...

    if not ok:
        fixed = replan(goal, reason)   # 피드백 주고 재계획
        for i, s in enumerate(fixed.steps, 1):
            print(f"  {i}. {s}")

    # --- 데모 2: 계획→검증→재계획 전체 파이프라인 실행 ---
    print("\n--- 전체 파이프라인 실행 ---")
    final_plan = plan_with_validation(goal)
    for i, s in enumerate(final_plan.steps, 1):
        print(f"  {i}. {s}")

1. 계획도 틀릴 수 있다

Plan-and-Execute의 약점은 03번에서 봤듯 "초기 계획이 틀리면 비효율적" 이라는 점입니다. LLM이 만든 계획이 이상할 수 있습니다.

# 나쁜 계획 예시들
Plan(goal="가을 패딩 출시", steps=["그냥 출시한다"])          # 1개뿐 → 분해 실패
Plan(goal="...", steps=["a", "", "c"])                       # 빈 단계 섞임
Plan(goal="...", steps=[1번, 2번, ..., 15번])               # 너무 많음 → 과분해

이런 계획을 그대로 실행하면 낭패입니다. 그래서 계획을 실행하기 전에 검증하고, 이상하면 다시 짜게 합니다. 사람도 일정표를 짠 뒤 "이거 너무 대충인데?" 하고 다시 짜잖아요.

2. validate_plan — 계획 검증

좋은 계획의 조건을 규칙으로 못 박습니다. (코드리뷰만)

MIN_STEPS, MAX_STEPS = 2, 8

def validate_plan(plan: Plan):
    """계획의 적합성을 판정한다. (적합여부 bool, 사유 str)를 돌려준다."""
    n = len(plan.steps)
    if n < MIN_STEPS:
        return False, f"단계가 {n}개뿐입니다 — 목표 분해가 부족합니다(최소 {MIN_STEPS}개)."
    if n > MAX_STEPS:
        return False, f"단계가 {n}개로 너무 많습니다 — 과분해입니다(최대 {MAX_STEPS}개)."
    if any(not s.strip() for s in plan.steps):
        return False, "빈 단계가 포함되어 있습니다 — 실행 불가능한 단계입니다."
    return True, "적합한 계획입니다."

세 가지를 검사합니다.

  • 너무 적음(< 2): 목표를 제대로 못 쪼갬(분해 실패).
  • 너무 많음(> 8): 과분해. 단계마다 실패 지점이 늘어 비효율.
  • 빈 단계: "".strip()이 빈 문자열인 껍데기 단계.

(적합여부, 사유) 튜플을 돌려주는 게 포인트입니다. 사유가 다음 단계(재계획)의 피드백이 됩니다.

3. replan — 피드백을 주고 다시 짜기

검증에 실패한 이유를 알려 주며 다시 계획하게 합니다.

def replan(goal: str, reason: str) -> Plan:
    """검증 실패 이유(reason)를 피드백으로 붙여 계획을 다시 세운다."""
    planner = llm.with_structured_output(Plan)
    prompt = (
        "너는 승승장구몰의 프로젝트 매니저다. 이전 계획이 다음 이유로 부적합 판정을 받았다.\n"
        f"부적합 사유: {reason}\n"
        f"이 점을 반드시 고쳐, 목표를 실행 순서대로 {MIN_STEPS}~{MAX_STEPS}개의 "
        f"구체적 하위 작업으로 다시 분해하라.\n목표: {goal}"
    )
    return planner.invoke(prompt)

핵심은 "무엇이 문제였는지"를 모델에 알려 주는 것입니다. "단계가 1개뿐이라 부족하다"고 알려 주면, 모델은 같은 실수를 반복하지 않고 더 나은 계획을 냅니다. 이건 3강 오분류 분석(틀린 걸 분석해 처방)과 같은 사고방식입니다.

4. 전체 파이프라인 — 계획 → 검증 → 재계획

이 세 조각을 묶어, 부적합하면 자동으로 다시 짜는 파이프라인을 만듭니다.

def plan_with_validation(goal: str, max_replan: int = 2) -> Plan:
    """계획 → 검증 → (부적합 시) 재계획을 최대 max_replan회 반복한다."""
    plan = make_plan(goal)
    for attempt in range(1, max_replan + 1):
        ok, reason = validate_plan(plan)
        print(f"[STEP {attempt}] 검증: {'적합' if ok else '부적합'} — {reason}")
        if ok:
            return plan                       # 통과 → 채택
        print(f"        → 재계획 요청(피드백: {reason})")
        plan = replan(goal, reason)           # 부적합 → 다시 짜기
    return plan

max_replan은 7강에서 배운 max_steps와 같은 안전장치입니다. 재계획을 무한히 반복하지 않게 상한을 둡니다.

5. 실행 — 잘못된 계획을 걸러내기

goal = "승승장구몰 신상품 '가을 패딩' 출시"

# 일부러 단계가 1개뿐인 나쁜 계획을 만들어 검증기가 잡는지 확인
bad_plan = Plan(goal=goal, steps=["그냥 출시한다"])
ok, reason = validate_plan(bad_plan)
print(f"검증: {'적합' if ok else '부적합'} — {reason}")
# → 부적합 — 단계가 1개뿐입니다...

if not ok:
    fixed = replan(goal, reason)   # 피드백 주고 재계획
    for i, s in enumerate(fixed.steps, 1):
        print(f"  {i}. {s}")

"그냥 출시한다"는 부실한 계획이 걸러지고, 피드백을 받아 제대로 된 5단계로 다시 짜였습니다.

6. 이 패턴의 의미 — 자가 검증

이 "생성 → 검증 → 실패하면 피드백 주고 재시도" 패턴은 AI 시스템의 핵심 안전장치입니다. 앞으로 계속 만납니다.

  • 10강: 코드 실행 실패 → 오류 피드백 → 재시도
  • 21강: 워크플로우 노드 검증
  • 27강: 분석 품질 부족 → 다시 수집

LLM의 출력을 그냥 믿지 않고 검증하고, 틀리면 이유를 알려 고치게 하는 거죠. 이게 신뢰할 수 있는 에이전트의 조건입니다.

핵심 정리

  • LLM이 만든 계획도 틀릴 수 있다(단계 부족·과다·빈 단계).
  • validate_plan으로 적합성을 판정하고 사유를 함께 돌려준다.
  • replan은 사유를 피드백으로 줘서 같은 실수를 막는다.
  • "생성 → 검증 → 재시도"는 신뢰할 수 있는 에이전트의 핵심 패턴.
