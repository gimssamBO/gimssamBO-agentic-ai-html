필요할 때만 검색하게

한 줄 요약

16강의 QA 체인은 무조건 검색합니다. "안녕하세요"에도 정책 문서를 뒤지죠. 사람 상담원은 일상 인사엔 그냥 답하고, 정책 질문이 오면 그제서야 정책집을 폅니다. 이 판단을 LLM에게 맡기는 게 Knowledge Agent입니다.

1. 항상 검색의 낭비

16강 RAG QA 체인은 강력하지만 한 가지 단점이 있습니다 — 무조건 검색합니다.

answer("안녕하세요!")        # → 정책 문서를 검색함 (불필요!)
answer("오늘 날씨 좋네요")    # → 정책 PDF를 뒤짐 (낭비!)
answer("환불 며칠 걸려요?")  # → 정책 검색함 (이건 필요)

"안녕하세요"나 "날씨 좋네요"는 정책 문서와 아무 관계가 없는데도 검색합니다. 이건 불필요한 임베딩 호출(비용)과 지연을 만듭니다. 인사 한마디에 문서를 뒤지는 건 비효율적이죠.

2. 사람 상담원은 어떻게 하나

진짜 상담원을 생각해 봅시다.

고객: "안녕하세요!"
상담원: "안녕하세요! 무엇을 도와드릴까요?"  ← 정책집 안 봄

고객: "환불 규정이 어떻게 되나요?"
상담원: (정책집을 펼치며) "환불은..."        ← 그제서야 정책집 봄

상담원은 판단합니다. 일상 인사엔 그냥 답하고, 규정 질문엔 자료를 찾죠. 매번 정책집을 펴 보지 않습니다. 이 "언제 자료를 볼지 판단하는 능력"이 핵심입니다.

3. RAG를 '도구'로 만든다

해결책: RAG를 하나의 도구(tool) 로 포장해 에이전트에게 쥐여 주는 것입니다.

에이전트(LLM) 가 [정책 문서 검색] 도구를 들고, 질문에 따라 판단합니다.

  • "안녕하세요" → 검색 도구 안 씀 → 바로 답
  • "환불 규정?" → 검색 도구 씀 → 근거로 답

5~12강에서 배운 그 패턴입니다 — LLM에게 도구를 주면 필요할 때 스스로 호출합니다. RAG 검색을 "도구 중 하나"로 만들면, 에이전트가 "이 질문은 검색이 필요한가?"를 판단하죠.

비유: 16강 QA 체인은 "모든 손님에게 무조건 정책집을 펴서 읽어 주는" 신입입니다. 17강 Knowledge Agent는 "손님 질문을 듣고 필요할 때만 정책집을 펴는" 노련한 상담원이죠. 후자가 훨씬 자연스럽고 효율적입니다.

4. RAG와 에이전트가 만난다

이 강은 두 흐름이 합쳐지는 지점입니다.

5~12강: 에이전트 (도구를 쓰는 LLM)
13~16강: RAG (문서 검색으로 답)
           ↓
17강: RAG를 도구로 → 에이전트가 필요할 때 검색

RAG 검색을 에이전트의 도구로 만드는 거죠. 그러면 에이전트가 주문 조회 도구, 재고 도구처럼 "정책 검색 도구"도 골라 씁니다. 12강의 멀티툴 에이전트에 "지식 도구"가 하나 더 생기는 셈입니다(18강에서 본격적으로 합칩니다).
