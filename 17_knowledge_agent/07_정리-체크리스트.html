정리 & 체크리스트

17강에서 배운 것

17강에서는 RAG를 도구로 만들어 "필요할 때만 검색하는" Knowledge Agent를 만들었습니다.

  • 항상 검색 vs 필요할 때: QA 체인은 무조건, 에이전트는 판단해서 검색.
  • create_retriever_tool: RAG를 LLM이 호출 가능한 검색 도구로 변환.
  • description = 라우팅 규칙: 에이전트가 "언제 검색할지" 판단하는 근거.
  • 일상/정책 구분: 같은 에이전트가 질문에 따라 검색 여부를 스스로 결정.
  • description 개선: 구체적·부정 조건으로 오호출을 줄임.

한눈에 보는 핵심 코드

from langchain_core.tools.retriever import create_retriever_tool
from langchain.agents import create_agent
from common import get_chat

# RAG retriever를 검색 도구로
policy_tool = create_retriever_tool(
    retriever,
    name="company_policy_search",
    description="환불/멤버십/직원 규정 등 사내 정책 질문에만 사용. 날씨·계산엔 사용 금지.")

# 에이전트에 연결 — 필요할 때만 검색
agent = create_agent(get_chat(temperature=0), tools=[policy_tool],
                     system_prompt="너는 상담원이다. 규정은 반드시 도구로 검색해 답하라.")

out = agent.invoke({"messages": [{"role": "user", "content": q}]})
used = any(getattr(m, "tool_calls", None) for m in out["messages"])  # 검색 여부

체크리스트

  • [ ] QA 체인(항상 검색)과 Knowledge Agent(필요할 때 검색)의 차이를 안다.
  • [ ] create_retriever_tool로 RAG를 에이전트 도구로 만들었다.
  • [ ] 도구 description이 "언제 검색할지"를 결정함을 이해했다.
  • [ ] 일상 질문엔 검색 안 하고 정책 질문엔 검색하는 것을 확인했다.
  • [ ] description을 구체화해 오호출을 줄일 수 있다.

한 줄 핵심

RAG를 도구로 만들면 에이전트가 "필요할 때만" 검색한다. 핵심은 도구의 description — 이게 곧 "언제 검색할지"를 정하는 라우팅 규칙이다.

다음 강 예고

17강은 검색 도구 하나만 다뤘습니다. 18강 RAG + Tool Agent에서는 17강의 정책 검색(문서)과 5~12강의 실시간 데이터 도구(주문·재고 조회)를 한 에이전트에 함께 넣습니다. "환불 정책 알려주고, 내 주문 환불 가능한지도 확인해줘" 같은 질문에서, 문서 검색과 DB 조회를 동시에 쓰는 RAG의 종착점입니다.
