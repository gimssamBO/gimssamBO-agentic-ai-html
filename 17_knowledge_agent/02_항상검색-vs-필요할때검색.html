항상 검색 vs 필요할 때 검색

한 줄 요약

QA 체인(16강) 은 모든 질문에 무조건 검색하는 고정 파이프라인이고, Knowledge Agent(17강) 는 에이전트가 판단해 필요할 때만 검색하는 추론 루프입니다. 단순함은 QA 체인이, 효율·유연함은 에이전트가 낫습니다.

1. 두 방식 비교

RAG QA 체인(16강) Knowledge Agent(17강)
검색 시점 모든 질문에 무조건 에이전트가 판단해 필요할 때만
일상 질문 불필요하게 검색 검색 없이 바로 답
구조 고정 파이프라인 도구 + 추론 루프(ReAct)
장점 단순·예측 가능 효율적·유연

2. QA 체인 — 고정 파이프라인

16강의 QA 체인은 정해진 길을 따릅니다.

질문 → 검색(항상) → 생성 → 답변

어떤 질문이 와도 이 흐름은 똑같습니다 — 무조건 검색하고, 무조건 생성합니다. 그래서:

  • 장점: 단순하고 예측 가능. "검색→생성"만 알면 됨.
  • 단점: 일상 질문에도 불필요하게 검색(낭비).

문서 질문만 들어오는 게 확실한 상황(예: 정책 Q&A 전용 봇)이라면 QA 체인이 깔끔합니다.

3. Knowledge Agent — 판단하는 루프

17강의 Knowledge Agent는 판단을 합니다.

질문 → LLM 판단:

  • 일상 질문? → 검색 없이 바로 답
  • 정책 질문? → 검색 도구 호출 → 답

7강에서 배운 ReAct 루프(생각→행동→관찰)가 여기서 작동합니다. 에이전트가 질문을 보고:

  • "이건 일상 인사네 → 검색 불필요 → 바로 답"
  • "이건 정책 질문이네 → 검색 도구 호출 → 근거로 답"

을 스스로 결정합니다. 그래서:

  • 장점: 효율적(필요할 때만 검색)이고 유연(다양한 질문 처리).
  • 단점: QA 체인보다 복잡하고, 판단이 가끔 틀릴 수 있음.

4. 무엇을 언제 쓰나

들어오는 질문이 '항상 문서 질문'인가?(정책 전용 Q&A 봇)

  • 예 → QA 체인 (단순하고 확실)
  • 아니오(일상 + 문서 질문 섞임) → Knowledge Agent (판단해서 검색)

승승장구몰 종합 상담봇처럼 일상 대화와 정책 질문이 섞여 들어오면 Knowledge Agent가 맞습니다. 반면 "정책 FAQ 전용 페이지"처럼 문서 질문만 들어온다면 QA 체인이 간단하죠.

5. 검색 여부를 어떻게 확인하나

에이전트가 실제로 검색했는지 코드로 확인할 수 있습니다. 메시지에 tool_calls가 있으면 도구(검색)를 호출한 것입니다.

out = agent.invoke({"messages": [{"role": "user", "content": q}]})
msgs = out["messages"]
# tool_calls가 하나라도 있으면 = 검색 도구를 호출했다는 뜻
used = any(getattr(m, "tool_calls", None) for m in msgs)
print("검색 도구 사용?", used)

tool_calls는 12강에서 본 그 도구 호출 기록입니다. 일상 질문엔 used=False(검색 안 함), 정책 질문엔 used=True(검색함)가 나오면, 에이전트가 제대로 판단하는 거죠. 04~05번에서 직접 확인합니다.

6. 둘은 대립이 아니라 선택

QA 체인과 Knowledge Agent는 "어느 게 더 좋다"가 아니라 상황에 맞는 선택입니다.

  • 단순·확실이 중요하면 → QA 체인
  • 효율·유연이 중요하면 → Knowledge Agent

이 강에서는 Knowledge Agent를 배우지만, QA 체인이 더 나은 경우도 많습니다. "도구를 많이 안다"보다 "상황에 맞게 고른다"가 좋은 엔지니어죠(28강 설계에서 다룹니다).

핵심 정리

  • QA 체인: 무조건 검색하는 고정 파이프라인(단순·예측 가능).
  • Knowledge Agent: 판단해 검색하는 추론 루프(효율·유연).
  • 일상+문서 질문이 섞이면 Knowledge Agent, 문서 전용이면 QA 체인.
  • tool_calls로 에이전트의 검색 여부를 확인할 수 있다.
  • 둘은 대립이 아니라 상황에 맞는 선택.
